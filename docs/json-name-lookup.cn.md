# JSON 属性名查找

[English edition](json-name-lookup.md)

LuminPack 为每个模型生成属性名查找表。顺序属性可以直接匹配下一个预期名称。乱序名称、转义解码后的名称和旧名称使用文档编码对应的生成查找方法。

在现代 Core 目标上，两个生成器都可以把普通类中连续、可直接写入的非 volatile `Int32` 字段作为一个有序字段组读取。生成代码比较带标点的完整字段头，并通过局部托管游标解析每个整数。一个分块读完或首次失配时，一次性发布已读前缀。普通 Reader 从第一个未读字段继续，保持原有语法校验、名称查找与复用行为。UTF-8 和 UTF-16 共用这套字段组结构。

小表按长度分派，再进行精确比较。较大的表如果每个长度组最多只有四个候选，也使用这条路径。生成器分别统计 UTF-8 字节长度和 UTF-16 代码单元长度，并计入旧名称与引用元数据。这是在编译期做出的选择，运行时不创建字典，也不选择查找策略。

同长度名称密集时，使用固定 seed 为零的 XXH3 64 位值分派。相同哈希常量归入同一 case，每个候选仍须通过完整名称比较。因此，哈希碰撞不会错误选择其他属性。XXH3 是非加密的分组函数，不能代替相等性比较，也不是安全边界。

Core 和两个生成器编译同一份 `XxHash3Algorithm.cs`，算法结果与标准 seed-zero XXH3 一致。UTF-8 对编码后的字节计算哈希；UTF-16 对代码单元的内存字节计算，不转码，也不做 Unicode 规范化。不同编码的哈希不要求相等；同一编码的编译期常量与运行时结果必须相等。

生成的哈希查找调用 `XxHash3.Hash64(ref byte source, uint byteLength)`。调用方必须提供已经验证的可读范围，只有零长度允许空引用。标量与向量内核均使用 GC 可跟踪的引用和 `Unsafe`，不使用指针，也不固定内存。便捷的 span 入口 `Hash64Utf8` 和 `Hash64Utf16` 转发到同一入口。这些是内部分派工具，不应用作持久化标识，也不能替代序列化 API。

不超过 240 字节的输入使用常量 secret 与标量混合。更长的输入在支持的现代 64 位目标上使用 AVX2 或 SSE2／ARM64 AdvSimd；AVX-512 机器使用 AVX2 路径。生成器与可移植目标使用标量实现；32 位运行时的宽字读取保留 Marshal 块复制规则。所有路径仅访问传入 span 的范围，不依赖原生库或运行时哈希包。

名称哈希不写入 JSON 或二进制记录。内部算法改变后，需要使用匹配的 Core 重新编译生成代码；不同算法版本之间不兼容已经编译的哈希常量。

实现改编自 .NET 10 `System.IO.Hashing` 和 xxHash。[第三方许可证](xxhash-LICENSE.txt) 统一保留在 `docs` 下，并随运行时与生成器包分发。

生成器定向检查为 `--verify-json-name-hash`：比较两个生成器与 Core 的结果，并对可移植 Core 执行真实生成的稀疏、密集查找、旧名称及引用元数据查找。运行前先构建 Release `netstandard2.1` Core。运行时 `MarshalCopyBlockTest` 包含独立标准向量、参考摘要、构造碰撞回归和保护页边界测试，并纳入既有 SIMD 与架构 CI 覆盖。
