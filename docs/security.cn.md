# 🛡️ 安全

[English](security.md) · [返回 README](../README.cn.md)

LuminPack 是带有性能导向原生存储路径的强类型序列化器。默认配置面向相互兼容、可信的数据生产方。仅有边界检查并不能让任意数据模型都适合处理恶意输入。应用的数据模型、生成的代码、格式化器和可选的原生内核都属于可信代码。

## 运行时支持与数据可移植性

运行时提供 `netstandard2.1` 和新版 .NET 资产。运行时可用性与数据可移植性是两种不同的保证。`netstandard2.1` 资产为 Unity/Mono/IL2CPP 使用指针游标：在托管内存上创建的底层读写器需要在整个生命周期内固定（pin）内存。生成的便捷入口保留自己的固定和清理逻辑。

原生基础类型和原始非托管存储保留进程的字节序和内存表示。原始结构体可能包含 padding、依赖运行时的布局以及指针大小的成员。持久化或网络协议中请避免 `IntPtr`、`UIntPtr`、指针、运行时大小的向量，以及无法分析的外部原生结构体。类型名称相同并不代表不同运行时版本之间 ABI 相同。

Packed 结构体按声明顺序去掉字段间的 padding。Tagged 集合对支持的布局差异建模，并用实际字段地址转换字段字节。两者都不是通用的字节序转换协议。跨机器交换需要相同的数据模型、帧与字符串选项、受支持的数据表示以及兼容的字节序，并在实际目标上用保留的夹具验证。版本容忍对象不会自动协商这些条件。

原生 padding 中可能是未定义或之前残留的字节。`Native` 复制完整存储。`Tagged` 在建模布局与运行布局一致时也可能复制完整存储（包括 padding）；在所有模型上都稳定的布局可以保留无头部的原生表示。这些决定只说明布局兼容，并不代表没有 padding 或输入可信。`Packed` 按声明顺序写字段的语义字节，不包含字段间的 padding。带 padding 的原始结构体可能泄露 padding 字节，或者对相等的字段值产生不同的字节序列；清空输出缓冲区并不能清除源数据中的 padding。公开协议请使用经过审查的按字段建模，或应用自己的规范线上格式。修改已经确定的原生线上字节需要单独做兼容性决定。

## 不可信输入

### 通过声明选择外部数据契约

在程序集或生成的根类型上使用现有的 `LuminPackOption` 特性。原有的序列化入口在编译期选择该策略，不存在额外的序列化入口。

```csharp
[LuminPackable]
[LuminPackOption(UntrustedData = true, MaxInputBytes = 1024 * 1024,
    MaxCollectionLength = 10_000, MaxDepth = 32)]
public partial class Request
{
    public int Id;
    public string Name = "";
}
```

默认值：编码输入 8 MiB、解压后负载 16 MiB、库的累计分配保守估计 64 MiB、每个集合 100,000 个元素、每个字符串 1,048,576 个 UTF-16 码元、100,000 个引用值、深度 64、32 Mi 工作单位。可通过 `MaxInputBytes`、`MaxDecompressedBytes`、`MaxAllocationBytes`、`MaxCollectionLength`、`MaxStringLength`、`MaxObjectCount`、`MaxDepth` 和 `MaxReadWork` 配置。限额必须非负；深度必须在 1 到 64 之间。设为 0 会拒绝任何需要该资源的操作。`MaxJsonDepth` 同样生效，并受这些文档的 `MaxDepth` 约束。程序集上的限额会被继承，类型上显式设置的限额覆盖它们。在单个成员上声明安全设置会被拒绝。

启用后的契约使用单独标识的二进制或 JSON 包络，其中包含生成的模型/配置摘要。双方必须使用相同的契约和字符串/配置选项。限额是接收方策略，不影响摘要。启用的契约与未加帧的可信记录不兼容；这是一个需要主动选择的协议，不是自动协商，也不是身份认证。JSON 使用规范的 `$luminpack`、`$schema`、`$value` 包络。二进制包络在解压前校验声明的压缩大小。便捷入口还会根据分配预算推导一个保守的字节上限，因此其实际输入上限可能小于 `MaxInputBytes`，span 重载也一样。各项限额都是上限，并不保证低于它们的每条记录都能满足累计预算。

该边界在解码前检查帧格式和模型/配置摘要，然后在原有格式化器运行过程中检查实际的计数、字符串、标量取值范围、已知的 JSON 成员、集合不变量和累计预算。按计数分配和 unsafe 访问之前都保留范围和资源检查。JSON 使用原有的严格分词器和转义解码器；字典条目必须恰好包含一个键和一个值。重复的名称、键和集合元素会被拒绝。集合不变量可以在有界构造之后、成功返回之前检查。对于未压缩的 span，不会完整复制输入，也不会预先扫描整份数据。压缩数据拥有单独限额的输出缓冲区；流、序列和字符输入保留必要的有界读入存储。

调用方必须在整个同步操作期间（包括应用回调期间）保持输入及其底层存储不变。并发修改输入，或在解码过程中把池化的输入还回去，都违反该契约。解码不是事务性的：在后期才发现的错误数据可能让已完成的字段或复用的存储保持更新状态，已经执行的回调也可能产生副作用。如果失败时不能改变共享状态，请解码到一个独立的应用对象中。写入方直接为原有操作加帧，执行输出字节限额并回填帧长度，不会重新校验完整输出。读取限额在接收时生效；写出的记录可能超出接收方的集合、深度或其他解码限额。

经过审查的形态包括：普通的非泛型生成对象、受支持的框架标量、可空标量、受支持的标准集合，以及显式 Packed 的非托管结构体。未知或自定义格式、由输入决定的类型、指针、原生大小的存储、Union/引用跟踪/版本容忍机制、压缩成员、旧版成员压缩操作、原始可空集合聚合以及其他未审查的形态，在该选项下都会直接拒绝。不使用该选项时，它们的可信实现仍然可用。有界的二进制包络压缩与旧版成员压缩是两回事。字典和集合的键需要经过审查的框架相等性；按文化排序的字符串键被排除。包含专用 Guid、DateTime、TimeSpan 或多维数组契约的 JSON 对象图会被拒绝，即使它们的二进制表示是被接受的。成员超过 256 个的 JSON 对象超出了经过审查的成员跟踪上限。

Packed 存储去掉 padding，但不实现通用的字节序转换。外部数据策略目前只接受小端运行时，拒绝其他字节序。互通仍然需要在实际目标上执行夹具测试。应用的构造函数、回调、比较器、手动注册的格式化器和原生扩展都属于可信代码：它们自己的分配、副作用和执行不计入库的预算。手动替换生成的派发不在该生成策略的保证范围内。保守的分配/工作量统计可能拒绝低于单项限额的输入，尤其是容易发生冲突的容器和线上占用为零的大型元素存储。

`UntrustedData = false` 是默认值。没有选择外部契约的对象图保留原有的生成代码和线上表示，没有运行时策略分派。可信的父对象可以包含单独选择了外部契约的子对象；子对象保留自己的包络和限额。关闭父对象的策略不会关闭单独选择的子对象。这种混合对象图可能在原有可信操作外包含未激活的保护适配层。启用后的校验、预算和包络有运行时开销；压缩、读入和部分集合检查可能分配内存。编译期选择只去掉了配置选择的开销，并没有去掉校验恶意输入所需的工作。更新后实现的兼容性和性能需要在实际目标上做针对性验证。

### 现有的可信契约与底层契约

前进式 Reader 的 public `EnsureReadable`、原有的 `Advance` 检查、固定值访问前检查、Union 帧检查以及动态集合/字符串负载检查在 Release 下都保持启用。span 入口在加载数据或修改目标之前拒绝过短的固定输入。仅基于地址的内核无法推断分配边界，由调用方保证范围有效。固定 Writer 存储要求输出空间已经预留。

有界的原始集合 API 拒绝包含托管引用的元素，这类类型需要生成的或专用的格式化器。把含托管引用的存储传给不检查的原始地址内核、把重叠范围传给不允许重叠的复制、使用失效指针或未固定的游标存储，都违反其契约。不要让输入数据控制这些 API 的指针或类型选择。

默认的可信操作不提供上面那些按声明选择的分配、对象数量、深度或工作量预算。合法输入仍然可能消耗大量资源。栈空间检查和压缩合理性检查不是应用级配额。请限制编码帧大小、解压前声明的大小、应用集合大小以及请求/进程资源。捕获内存或栈耗尽异常不是资源控制策略。

Packed 的空结构体占 0 字节负载。因此，这种元素组成的合法集合可能只有计数和帧，而与元素数量无关。生成的读取代码保留这种表示，只对经证明为空的 Packed 契约使用最小值 0。仅限制编码输入大小无法约束这种集合的分配或遍历工作量；在不可信边界上需要单独的元素/工作量配额。

压缩的原始集合要求帧中声明的解码字节宽度，等于经过检查的元素数量乘以存储宽度，才会分配或写入目标。一个合法但更短的压缩帧并不是合法的完整集合负载。这项一致性检查不能替代应用的解压配额。

默认 JSON 配置 `ValidateJsonSyntax = false`、深度 1024，是面向可信 JSON 的配置。处理外部 JSON 时，请选择 `ValidateJsonSyntax = true` 且深度合适的无状态配置。严格语法仍然需要配合应用的资源和模型限制。

经批准的集合快速路径假定数据生产方满足不变量。原始集合的桶重建不承诺拒绝重复元素；恶意的哈希冲突和应用比较器可能代价很高。原始标量位并不对每种框架类型做取值范围校验。把解码数据用于正确性或授权判断之前，请检查唯一性和取值范围不变量。

构造函数、回调、池化/复用处理以及自定义格式化器都可能在读取过程中执行应用代码。读取失败时，已完成的字段可能按现有的发布规则保留。反序列化既不是事务，也不是执行沙箱。把边界对象发布到应用状态之前，请先校验它。

在启用动态代码的配置下，`System.Type` 反序列化会解析输入中提供的名称。请把它排除在面向恶意输入的模型之外，或使用应用自己的封闭标识映射。动态代码能力检查不是类型白名单；仅按名称解析类型本身也不意味着可以构造任意对象或执行代码。

## 认证与原生扩展

序列化本身不提供真实性或机密性。单独的 ChaCha20-Poly1305 工具在解密到目标之前先验证认证标签，标签比较保持在常数时间路径上。密钥管理、每个密钥下 nonce 的唯一性以及认证的协议上下文仍由应用负责。需要互通时请使用标准的 256 位密钥 RFC 8439 构造。

仅 `netstandard2.1` 提供的 `LuminPackBurst` 表是可信的原生扩展点，绝不会由负载数据初始化。其中的指针必须遵守[原生 Hook 契约](burst-hooks.cn.md)。托管层的计数检查无法挽回错误的原生内存访问。只启用在实际运行时和 CPU 上验证过的后端。

编译、合成布局和已配置的 CI 任务都不能证明在每个目标上的实际执行。请遵循 [SIMD 规则](mechanism-contract.cn.md#4-simd)。
