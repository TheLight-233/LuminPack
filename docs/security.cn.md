# 🛡️ 安全

[English](security.md) · [返回 README](README.cn.md)

LuminPack 是带有性能导向原生存储路径的强类型序列化器。默认配置面向相互兼容、可信的数据生产方。仅有边界检查并不能让任意数据模型都适合处理恶意输入。应用的数据模型、生成的代码、格式化器和可选的原生内核都属于可信代码。

## 运行时支持与数据可移植性

运行时提供 `netstandard2.1` 和新版 .NET 资产。运行时可用性与数据可移植性是两种不同的保证。`netstandard2.1` 资产为 Unity/Mono/IL2CPP 使用指针游标：在托管内存上创建的底层读写器需要在整个生命周期内固定（pin）内存。生成的便捷入口保留自己的固定和清理逻辑。

原生基础类型和原始非托管存储保留进程的字节序和内存表示。原始结构体可能包含 padding、依赖运行时的布局以及指针大小的成员。持久化或网络协议中请避免 `IntPtr`、`UIntPtr`、指针、运行时大小的向量，以及无法分析的外部原生结构体。类型名称相同并不代表不同运行时版本之间 ABI 相同。

Packed 结构体按声明顺序去掉字段间的 padding。Tagged 集合对支持的布局差异建模，并用实际字段地址转换字段字节。两者都不是通用的字节序转换协议。跨机器交换需要相同的数据模型、帧与字符串选项、受支持的数据表示以及兼容的字节序，并在实际目标上用保留的夹具验证。版本容忍对象不会自动协商这些条件。

原生 padding 中可能是未定义或之前残留的字节。`Native` 复制完整存储。`Tagged` 在建模布局与运行布局一致时也可能复制完整存储（包括 padding）；在所有模型上都稳定的布局可以保留无头部的原生表示。这些决定只说明布局兼容，并不代表没有 padding 或输入可信。`Packed` 按声明顺序写字段的语义字节，不包含字段间的 padding。带 padding 的原始结构体可能泄露 padding 字节，或者对相等的字段值产生不同的字节序列；清空输出缓冲区并不能清除源数据中的 padding。公开协议请使用经过审查的按字段建模，或应用自己的规范线上格式。修改已经确定的原生线上字节需要单独做兼容性决定。

## 不可信输入

### 默认按不可信数据读取

除非声明另有指定，生成的二进制读取都把输入视为不可信数据。记录保留普通线格式和写入端，只有生成的读取发生变化：它们在实际读取输入的位置进行检查，限额以常量形式固化在生成代码中：

- **边界。** Reader 在 Debug 和 Release 中对每次加载做输入边界检查。集合或字符串的计数不可能要求超过剩余输入的字节数，因此分配始终与实际消耗的输入成比例。
- **对象标记。** 对象的成员标记必须等于其声明的成员数或 null 标记。
- **Boolean 值域。** Boolean 字段、Boolean 数组和 `List<bool>` 拒绝 `0` 和 `1` 以外的所有存储值。批量存储在现代 .NET 上使用有界向量加载，在所有目标上使用按字分组检查。
- **版本容忍记录。** 前缀、成员数、成员宽度和负载长度都按输入和读取方模型检查，每个成员的读取必须恰好结束在其记录的长度处。
- **引用跟踪。** 回引必须指向已经读过且类型与该位置预期一致的对象；原始槽位必须记录其精确宽度。未知槽位按记录的长度跳过。
- **Union。** 未声明的标签会被拒绝。分支负载以相同的检查读取，并使用外层根的限额。
- **压缩集合。** 在分配任何存储之前，声明的元素数必须与压缩帧一致，且不能超过其编码字节所能产生的大小。

限额在声明之前不设上限。在程序集或生成的根类型上通过 `LuminPackOption` 声明：

```csharp
[LuminPackable]
[LuminPackOption(MaxInputBytes = 1024 * 1024, MaxCollectionLength = 10_000, MaxStringLength = 4096, MaxDepth = 32)]
public partial class Request
{
    public int Id;
    public string Name = "";
}
```

`MaxCollectionLength` 限制每个二进制集合，`MaxStringLength` 限制每个二进制字符串（以 UTF-16 码元计）。`MaxDepth` 限制递归值的嵌套层数；生成器只在递归类型中计数深度，因为其他对象图都有有限的静态深度。未声明时，递归读取保留其栈保护。`MaxInputBytes` 限制生成入口接受的输入大小，包括流和序列的暂存。不设上限的限额是 JIT 会消除的常量，因此未声明的限额没有开销。限额必须非负；设为 0 会拒绝任何需要该资源的值。程序集上的限额会被继承，类型上显式设置的限额覆盖它们。通过根读取的嵌套类型使用根的限额；通过可信父对象读取的类型使用它自己的限额。`MaxDecompressedBytes`、`MaxAllocationBytes`、`MaxObjectCount` 和 `MaxReadWork` 已过时且不再生效。在单个成员上声明安全设置会被拒绝。

显式选择恶意输入处理的声明（`UntrustedData = true` 或任意 `Max*` 限额）在读取 JSON 时，除 `MaxInputBytes` 外还使用严格语法（`ValidateJsonSyntax`），并在声明时使用 `MaxDepth` 文档深度。没有这类声明时，JSON 保持声明的配置。集合和字符串限额作用于二进制记录；JSON 值受文档大小约束。

在程序集或类型上声明 `UntrustedData = false`，即可用不检查的读取和宽松的 JSON 语法读取可信数据。可信父对象可以包含不可信子对象；子对象保留自己的检查。

所有生成的形态都被接受：对象、版本容忍和引用跟踪记录、Union、泛型模型、框架值类型与集合、压缩成员以及原始非托管结构体。Custom 格式和手动注册的格式化器属于应用代码，仍按可信代码处理。只有由输入决定的类型（`object`、`System.Type`、委托、反射类型和非泛型框架接口）会以 `NotSupportedException` 直接拒绝；若这类模型只读取可信数据，请声明 `UntrustedData = false`。

这些检查不是模式证明，也不是身份认证。枚举值、字符、decimal 和 DateTime 存储、原始非托管结构体（包括其中的 Boolean 字段）、原始可空元素、其他框架容器中的 Boolean，以及字符串内容（单独的 UTF-16 代理项）按存储值接受；UTF-8 字符串与所有记录一样严格解码。字典和集合的读取使用框架相等性；恶意构造的键集合仍可能在哈希表中冲突，请按可接受的工作量声明 `MaxCollectionLength`。零宽 Packed 结构体的集合每个元素不消耗负载字节，因此只有 `MaxCollectionLength` 能约束它。应用的构造函数、回调、比较器、自定义格式化器和原生扩展仍属于可信代码。

调用方必须在整个同步操作期间（包括应用回调期间）保持输入及其底层存储不变。解码不是事务性的：在后期才发现的错误数据可能让已完成的字段或复用的存储保持更新状态，已经执行的回调也可能产生副作用。嵌套对象只有在自身读取成功后才会发布到父对象。如果失败时不能改变共享状态，请解码到一个独立的应用对象中。

### 现有的可信契约与底层契约

前进式 Reader 的 public `EnsureReadable`、原有的 `Advance` 检查、固定值访问前检查、Union 帧检查以及动态集合/字符串负载检查在 Release 下都保持启用。span 入口在加载数据或修改目标之前拒绝过短的固定输入。仅基于地址的内核无法推断分配边界，由调用方保证范围有效。固定 Writer 存储要求输出空间已经预留。

有界的原始集合 API 拒绝包含托管引用的元素，这类类型需要生成的或专用的格式化器。把含托管引用的存储传给不检查的原始地址内核、把重叠范围传给不允许重叠的复制、使用失效指针或未固定的游标存储，都违反其契约。不要让输入数据控制这些 API 的指针或类型选择。

可信操作（`UntrustedData = false`）不检查上面所述的对象标记、Boolean 值域以及集合、字符串和深度限额。合法输入仍然可能消耗大量资源。栈空间检查和压缩合理性检查不是应用级配额。请限制编码帧大小、解压前声明的大小、应用集合大小以及请求/进程资源。捕获内存或栈耗尽异常不是资源控制策略。

Packed 的空结构体占 0 字节负载。因此，这种元素组成的合法集合可能只有计数和帧，而与元素数量无关。生成的读取代码保留这种表示，只对经证明为空的 Packed 契约使用最小值 0。仅限制编码输入大小无法约束这种集合的分配或遍历工作量；在不可信边界上需要单独的元素/工作量配额。

压缩的原始集合要求帧中声明的解码字节宽度，等于经过检查的元素数量乘以存储宽度，才会分配或写入目标。一个合法但更短的压缩帧并不是合法的完整集合负载。每次读取还会在分配之前拒绝超过编码负载 256 倍的声明宽度，LuminZ 无法产生这样的输出。这些一致性检查不能替代应用的解压配额。

默认 JSON 配置为 `ValidateJsonSyntax = false`、深度 1024。显式的恶意输入声明会选择严格语法；否则处理外部 JSON 时请选择 `ValidateJsonSyntax = true` 和合适的深度。严格语法仍然需要配合应用的资源和模型限制。

经批准的集合快速路径假定数据生产方满足不变量。原始集合的桶重建不承诺拒绝重复元素；恶意的哈希冲突和应用比较器可能代价很高。原始标量位并不对每种框架类型做取值范围校验。把解码数据用于正确性或授权判断之前，请检查唯一性和取值范围不变量。

构造函数、回调、池化/复用处理以及自定义格式化器都可能在读取过程中执行应用代码。读取失败时，已完成的字段可能按现有的发布规则保留。反序列化既不是事务，也不是执行沙箱。把边界对象发布到应用状态之前，请先校验它。

在启用动态代码的配置下，`System.Type` 反序列化会解析输入中提供的名称。请把它排除在面向恶意输入的模型之外，或使用应用自己的封闭标识映射。动态代码能力检查不是类型白名单；仅按名称解析类型本身也不意味着可以构造任意对象或执行代码。

## 认证与原生扩展

序列化本身不提供真实性或机密性。单独的 ChaCha20-Poly1305 工具在解密到目标之前先验证认证标签，标签比较保持在常数时间路径上。密钥管理、每个密钥下 nonce 的唯一性以及认证的协议上下文仍由应用负责。需要互通时请使用标准的 256 位密钥 RFC 8439 构造。

仅 `netstandard2.1` 提供的 `LuminPackBurst` 表是可信的原生扩展点，绝不会由负载数据初始化。其中的指针必须遵守[原生 Hook 契约](burst-hooks.cn.md)。托管层的计数检查无法挽回错误的原生内存访问。只启用在实际运行时和 CPU 上验证过的后端。

编译、合成布局和已配置的 CI 任务都不能证明在每个目标上的实际执行。请遵循 [SIMD 规则](mechanism-contract.cn.md#4-simd)。
