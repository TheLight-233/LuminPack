# Mechanism contract

[Chinese](mechanism-contract.cn.md)

This document lists the hard constraints of LuminPack. It applies to the whole repository: runtime code, the generator, generated code, optional modules and conditional targets. A passing round trip, a smaller file or a faster benchmark is never a reason to replace one of these mechanisms on its own.

The history of individual approvals lives in Git. When this document, the code and the history disagree, report the discrepancy with evidence instead of silently picking a design.

## 1. Change control

1. **Mechanisms are preserved by default.** Every mechanism in section 2 stays as it is unless the owner explicitly approves a concrete replacement.
2. **Experiments come first.** A faster alternative is prepared in `experiments/` (kept out of version control), with:
   - before/after elapsed-time ratios against the same reference libraries (for example Nino, MemoryPack, System.Text.Json), measured on the same machine, fixture, runtime and options, in the same run;
   - repeated samples with their dispersion, and allocations;
   - generated source, IL or native code where it matters;
   - the semantic, API, wire, ownership and platform trade-offs.
3. **Only explicit approval of that concrete proposal authorizes the replacement.** A performance target, a refactoring, dead-code removal or a size reduction is not approval.
4. **Correctness fixes are distinct.** A reproduced bug may be fixed while keeping the intended protocol. Record it as a fix with its regression test, not as an unchanged implementation.
5. **Approved differences are recorded.** Add the approved rule to this document (not a dated narrative) and describe the change in the commit.
6. **Commit completed work by default.** After completing a feature or fix and its relevant verification, commit only the task's changes using the [commit conventions](../CONTRIBUTING.md#commit-conventions), without asking for commit permission. Exclude unrelated or unfinished changes. Ask whether to push after committing unless the owner has already authorized that push. Tags and published-history rewrites still require explicit authorization.

## 2. Preserved mechanisms

### Storage access

- **Local + As views.** Private, protected, readonly and auto-property backing storage is accessed through generated layout mirrors and `Unsafe.As`, never reflection. Mirrors replicate the inheritance chain and `LayoutKind` (including explicit offsets). Accessible writable fields are accessed directly.
- **Storage placeholders.** Mirror fields, padding members and hidden storage must not be removed because ordinary call-site searches find no use.
- **Adjacent-field bulk copies.** Consecutive unmanaged fields may be copied as one block only on 64-bit, after proving the actual field addresses match the packed offsets, excluding volatile fields, and keeping a field-wise fallback.
- **Architecture-specific fixed access.** On 32-bit, an individual unmanaged value with `Unsafe.SizeOf<T>() <= 4` may use typed `Unsafe.ReadUnaligned` / `WriteUnaligned`. Larger values and field batches use `LuminPackMarshal.CopyBlockUnaligned` and the packed storage views, because typed unaligned access of those can crash IL2CPP. All members being four bytes or smaller does not permit a typed aggregate access. On 64-bit, typed access and block copies are both allowed.
- **Raw copies.** Non-overlapping block copies, including generated ones, go through `LuminPackMarshal.CopyBlockUnaligned`; only that helper calls `Unsafe.CopyBlockUnaligned`. Overlap-safe span copies keep memmove semantics.

### Representations

- **Object mode** is positional with a one-byte member count (0 to 249, `255` = null).
- **Version tolerance** uses named members with UTF-8 metadata, a member width table and byte-wise metadata comparison; `LuminPackOldName` keeps the oldest name on write. Revision 2 records are written in one pass: raw members at their table width, variable members behind an `int` length. Readers keep accepting revision 1 records.
- **Reference tracking** (`CircleReference`) keeps its slot tables and explicit reference ids. The table holds one width byte per slot (a raw width, `0` for an empty slot, `255` for a value behind its `int` length), so records are written in one pass and a reader whose table matches compares it as constant words and reads straight into the object. Unknown trailing slots are skipped, and explicit ids keep later back references exact after a skip. Writers find the first few objects of an operation by a reference scan before hashing; readers store sequential reference ids in an array and test reuse candidates with one probe that also registers them.
- **Unmanaged structs** keep the `StructLayout` contract: `Tagged` (default), `Packed`, `Native`.
- **Strings** default to fixed-width UTF-16 length records, with the compact Latin-1 form; UTF-8 and token profiles stay available. Opt-in `VarInt` recording encodes each existing length header plus one as canonical unsigned base-128, preserving payload encodings and distinct null and empty records. UTF-8 keeps both length fields. Fixed-width defaults and their wire bytes remain unchanged; both endpoints select the same profile. Token records share the empty terminator.
- **JSON** keeps its envelopes (`$type`/`$value`, `$id`/`$ref`, `Lazy`, multidimensional arrays) and rejects non-finite numbers.
- **Canonical JSON clock reads.** On modern .NET, the built-in UTF-16 length profile can parse the exact `HH:mm:ss.fffffff` token for `TimeOnly` and nonnegative sub-day `TimeSpan` under invariant current culture. The reader validates and snapshots the token and completes the value before the bounded digit checks and construction. Other forms, cultures and profiles use the existing parser.
- **Canonical JSON date reads.** Modern Core may parse the exact invariant `yyyy-MM-dd` form of an already decoded `DateOnly` token with bounded ASCII digit and Gregorian calendar checks. Next selects the helper when the referenced runtime exposes it. Keep the existing token completion and fallback to the framework round-trip parser for other forms and invalid dates.
- **Canonical JSON timestamp reads.** On modern .NET, the built-in UTF-16 length profile under invariant current culture may parse the exact round-trip `DateTime` form with a UTC marker and the `DateTimeOffset` form with an explicit signed offset. After existing validation, private token capture and value completion, narrow the bounded ASCII token and require the framework round-trip byte parser to consume it in full. Other forms, cultures and profiles use the original parser.
- **Reference-tracked JSON property heads.** On 64-bit modern .NET, generated writers may copy a complete static property head into the current window and advance once for both contiguous and segmented output. The head uses the document encoding and the current separator state. A short window or an unsupported profile uses the original property writer, preserving output callbacks, committed prefixes and reference registration order.
- **Ordinary JSON integer runs.** For consecutive directly writable, nonvolatile `Int32` fields, the generated reader may match complete static heads and decode plain integers in a bounded local managed window. Publish only the successfully consumed prefix at a chunk boundary or before falling back. Preserve per-field publication, separator grammar, reuse, and the ordinary parser at the first unmatched field.
- **Byte order** is little-endian. No mode performs endian conversion.
- **Compression** uses `LUM2` frames with single-byte length extensions below 255 and an escaped canonical unsigned base-128 remainder for longer lengths, a 64 KiB match window and the per-thread position table. High-ratio allocating reads validate complete sequence structure before allocation. Earlier `LUMZ` frames are rejected. Match hooks, bounded SIMD tails, decoder checks and 32-bit access rules remain in force; see [compression](compression.md).
- Changing any wire byte needs explicit approval and updated wire fixtures.

### Dispatch

- **Named member kernels.** Source-owned, non-generic positional classes without inheritance, callbacks or bounded-record declarations may share a concrete static member writer when their members are public raw storage or strings and at least one member is a string. Purely fixed records keep their existing compact stores. Preserve the original member header, field-address proofs, fixed stores, string operations and compiled member profiles; do not replace them with the standalone root's capacity fusion. Member kernels retain an inline hint, while their callers leave root inlining to the runtime. Complete public-field writes consisting only of runtime record kernels and unscoped named member calls may lower directly from existing type facts. All other contracts retain their existing operation projection. This adds no runtime plan, formatter witness or payload dispatch and removes no existing entry.
- **Next nested record entries.** JSON nested fields use the concrete formatter's document-profile entry. A positional binary child may use its existing object or payload read only where it preserves the original header, checked-input policy, field-address proofs and partial-read behavior. Stage the child locally so a newly allocated instance is published only after a successful member read. Existing binary member writers and standalone writers with equivalent stores may be called directly. Preserve the original member write where the standalone entry reserves output differently.
- **Static entries** use compiler interceptors when versioned interception locations and C# 11 or later are available. Closed payload calls, including explicit generic syntax, bind the existing concrete roots without payload dispatch, reflection or delegate caches. Explicit profiles use both payload and profile type arguments; no backend emits payload-specific profile convenience overloads on the public facade. Concrete state forwarders have payload-specific names on statically integrated paths; convenience entries live in payload-specific containers. No new runtime plan or formatter witness is introduced. Older compilers use the installed IL postprocessor with the same generated entries and exact signature mappings. It substitutes local static call operands, validates stack types, preserves portable symbols and requires the original signing key for signed images. When both integrations are disabled, default calls retain concrete overloads and explicit profiles use registered generic fallback.
- **Internal state forwarding in applications.** In executable projects with compiler interception and without friend access, an exact single-call state interceptor may call its existing nested root directly. Its signature, profile and passing conventions stay intact. A payload-specific internal forwarder may be omitted only when the completed contributions and consumer source leave it without a reference and its declaration is unambiguous. Libraries, friend assemblies and the IL rewriting backend retain their state forwarders and binding contracts.
- **Source generic wrappers** may be specialized at closed calls when their static source bodies can be relocated safely. Preserve argument evaluation, overload selection, caller information, side effects and correlated method/enclosing-type arguments. Opaque or unsupported bodies keep the original call and registered fallback. Interception never rewrites referenced assemblies or virtual dispatch.
- **Next static entries.** Next intercepts only facade calls with a closed payload. Each interceptor calls the existing static root and implements its required document boundary. Explicit profiles share the interceptor's profile type parameter. Open payload calls in source generic wrappers use registered fallback without interprocedural expansion. Generated XML documents the public facade.
- **Generic fallback entry points** serve explicit and `Custom` registrations. Next also publishes the emitted operations of discovered closed payloads in a consuming-assembly table and uses Core-owned built-in scalar and string registrations. The facade initializes these registrations on first use, and explicit operations take precedence. Missing registrations or operations throw `LuminPackException`. Disabling registration disables the fallback. No runtime type discovery or reflection factory is used. Fallback document boundaries use the consuming assembly defaults or the explicit profile, while intercepted concrete roots keep declaration-owned options. A generic spelling alone no longer requests registered dispatch when its payload can be intercepted.
- **Union dispatch** is a generated public virtual method on the root (`EditorBrowsable(Never)`). Generic Union roots add a cached slot switch after that virtual call. No generic virtual methods or replacement switches.
- **Exact binary Union writes.** On every target, the compiled binary slots of an eligible local, non-generic abstract class root select generated cases by exact runtime type equality in tag order. Unmatched runtime types go directly to the existing registration lookup or unknown-case error. A provably closed single sealed case can keep its direct call. The generated virtual slots remain callable. JSON, generic and interface roots, ineligible roots and offset calculations keep their existing dispatch.
- **Union collections.** Lists, single-dimensional arrays, `ImmutableArray<T>` and dictionaries use the root's write tier for each element in input order. Dense dictionary writers apply that same tier within their existing fixed Union cursor protocol. Payload width does not change the tier or string representation.
- **Fresh Union elements.** Newly allocated Union collection storage may read through a zero-initialized local before assigning the element, preserving the Union operation's existing publication after successful payload reading. Existing elements retain their reuse path; ordinary objects and Custom formatters retain their own publication contracts.
- **Fresh fixed Union reads.** Next may use the existing checked block reader for an allocated, non-pooled fixed case on a 64-bit modern target. The case has no callbacks and the run has directly writable, nonvolatile, unmanaged fields without Boolean validation. Prove the actual field addresses before using the block and keep the field-wise fallback. A reused exact case may use the same checked block, because the complete run is validated before any byte is copied; the reuse arms store the slot only when the case object changes. Validate the full input before moving the cursor or writing the batch, and publish the new case only after the payload succeeds.
- **Registration** passes typed delegates (`LuminPackFormatter`) without requiring an unsafe context. Conditional weak tables retain complete registrations for the payload type's lifetime; MethodTable indexes hold weak references, allowing collectible payload assemblies to unload. Delegates and captured targets remain alive while their payload registration is alive. Registering collectible code for a noncollectible payload retains that code for the payload's lifetime. Registration validates tags, case types and required operations before publishing.
- **`Custom`** formatters own their complete representation and are invoked through their registered delegates.

### Execution state

- **Advancing cursors.** Binary and JSON readers and writers use a `ref byte` cursor on modern .NET and a one-element `Span<byte>` to carry the managed cursor address on `netstandard2.1`. The span length describes the cursor representation. The retained window and cached end define the accessible range. Low-level callers can get the cursor reference through `MemoryMarshal.GetReference`.
- **Cached ends.** Writer, Reader, JSON Writer and JSON Reader cache the end of their window (or the writer's growth threshold) beside the cursor. `Buffer`, `BufferCheckLimit` and `Owner` have public getters and internal setters that refresh the cache; every constructor and window change must refresh it.
- **Cursor publication.** Generated code may keep the cursor in a local between state-observing boundaries. It must publish the cursor before calling a formatter, a Union or recursive operation, a callback, or a capacity check, and resume from the resulting state afterwards. Never keep a buffer reference across a resize.
- **Scalar reads.** Generated scalar loads call `LuminPackReader.Read`. A fixed batch or a sequence window may use the address-based overload after validating the entire range. The Reader owns the 32-bit scalar access decision. Storage proofs and validation for batched and untrusted reads still apply.
- **Fixed Union case writes.** An eligible local, narrow, non-generic class Union's ordinary virtual case slot may write its tag and callback-free fixed payload in the shared cursor-returning body, publishing the resulting position before returning. It keeps the original virtual and profile-specific slots, and excludes external-input policy cases; other cases retain their original write path.
- **Large fixed Union records.** Fixed payloads whose width plus the maximum Union header exceeds the ordinary minimum growth headroom reserve their complete payload before its unchecked stores. The returning body publishes its absolute cursor before that capacity boundary and reacquires output storage after growth. Small fixed payloads keep their threshold-based reservation contract.
- **One state body per operation.** Each retained type has one complete body for each operation that is generated (binary write, binary read, JSON write, JSON read; see automatic generation); convenience overloads forward to it. Direct records also keep one exact-width body for their allocating write. A wide binary writer may reuse a closed framework collection writer for repeated compound-element traversals outside loops and capacity reservations. It passes the original state and compiled member profile. Exceptionally wide binary readers may split complete member branches into static local functions that share the original reader by reference and act on the same class instance. Validation, cursor movement and publication on failure keep their original order.
- **Managed output storage.** `LuminBufferWriter` owns one `ArrayPool<byte>.Shared` array. On every target a `GCHandle` pins each newly rented array before the writer measures its 64-byte alignment offset. It stays pinned until return, preserving the alignment across GC. Growth keeps the 32 KiB initial capacity, 1.5x growth and 87.5% threshold. It extends in place while the array fits or copies to a newly pinned array before unpinning and returning the previous array, then refreshes the cursor and end caches. The owner clears or writes every exposed byte. A finalizer frees the pin of an abandoned rental. Explicit disposal or return can recycle the array.
- **Caller-owned append sessions.** Overloads taking a `LuminBufferWriter` append at its cursor and keep reference state until the caller resets it (`ResetForReuse`, `Reset`, `ResetCore`).
- **Independent default reference contexts.** Separate default readers and writers never share reference identities.
- **Fresh JSON sequence capacity.** Fresh List/Queue storage, ordinary sequence interfaces, Collection/ObservableCollection and their read-only wrappers may use a read-only structural capacity hint before their original element loop. Grouping/Lookup element lists share that rule. Existing targets keep their original reuse/publication and callbacks; unavailable hints or later count changes keep growth fallback. Tiny inputs skip sizing. Fresh Capacity may change and the extra scan may cost CPU; avoiding growth allocations has priority. Arrays and hash-set/map/Lookup dictionary construction retain their original paths; optional-helper metadata is checked before emission.
- **Next ObjectModel wrapper formatters.** Exact framework wrappers over known lists or arrays, and the sealed collection builder, may batch UTF-16 length strings and UTF-8 JSON integers through the existing span kernels. Versioned storage checks its enumeration version across output boundaries and reloads the backing array after capacity changes. Other storage and profiles use the original formatter loop. JSON observable insertion checks exact type and listener state after each element formatter. A capacity hint may size fresh wrapper or builder storage before the original element loop.
- **Next collection interface writes.** Exact framework lists, arrays, sets and dictionaries may select their concrete traversal. The original interface enumeration remains available for derived and arbitrary implementations. Mutable dictionary interfaces may write each callback-free raw pair after one complete bounds check. The count is patched after enumeration, and the original per-member path handles short output windows. JSON may combine the separator and integer element or pair in the existing logical record. On modern .NET, the binary owned writer may use the legacy counted span and complete per-object reservation for exact List storage, built-in UTF-16 length profiles and callback-free positional records whose variable members are strings or raw scalar lists. Array and arbitrary interface implementations, custom profiles and span destinations keep their existing paths.
- **Next concrete map records.** In binary, a nonempty run of raw pairs in validated sorted-list arrays or a private sorted-dictionary lease may use one complete output check. The original scalar loop handles short windows. A fresh dictionary of fixed integer pairs may read directly into proven storage after validating the complete payload. JSON integer entries may combine framing with numeric writes. Exact sorted-list JSON traversal captures both members before writing either and checks the mutation version at each original enumeration boundary, including the final one. The bounded UTF-16 pair writers also recognize declaration-owned wrappers of the built-in UTF-16 length and default profiles. A dense binary dictionary with a raw key may omit the value formatter’s preliminary growth check when the whole key fits before the growth threshold. The boundary path checks capacity and captures the value before its original threshold operation.
- **Parallel dictionary storage.** Sorted-list and frozen dictionary binary writers may use one capacity proof per fixed UTF-16 string and unmanaged pair from validated parallel storage. The established scalar fallback retains key-before-value loading across output growth. JSON sorted-list traversal retains its version checks and value capture order.
- **Next contiguous collection runs.** Exact `int` and `long` spans may write JSON elements with a local cursor in the current output window. Short or overlapping windows and UTF-16 cultures with user callbacks use the original scalar operations and input-load order. Segmented UTF-16 length string writes may use the existing binary string-run kernels under both the storage bound and the original growth threshold. They keep the accumulated count backpatch and the scalar check at the next record boundary. Rectangular JSON arrays keep their shape envelope and copy the validated staging span into the result in row-major order. The storage address comes from the framework array-data API or the typed cell at the declared lower bounds on older targets.
- **Next mutable stack, queue and heap records.** Exact validated stacks may move reference-free binary storage in bottom-first order within a proven window and publish a direct refill only after the complete payload check. String stacks and wrapped string queues may use the checked UTF-16 length record runs. A failed staged string read leaves the stack empty and clears reference slots. UTF-8 integer stack and queue writers can format directly across output windows. They capture the current item before a separator or value can call the output owner and check the enumeration version before continuing, including after the final item. Priority queues keep heap enumeration order. A complete raw binary window can write the two fields without tuple padding, and a fixed scalar reader with the default comparer can accept a checked heap-order prefix before returning to ordinary insertion. On x64 with SSE and SSE2, packed pairs of a four-byte element and an `Int32` priority may check each group of four children against their shared parent with one vector comparison and copy the group; the scalar check resumes at the first rejected group. JSON can reuse the bounded integer entry writer and a capacity hint for large fresh heaps with string members while preserving existing comparers, entry grammar, partial-read publication and fallback operations.
- **Deep JSON lookahead storage.** CountArrayElements owns an independent deep-grammar copy, may rent/grow that private copy from ArrayPool<byte>.Shared, and returns it in finally on success or failure. The original reader storage and all state remain unchanged. Ordinary reader-owned deep grammar retains its original allocation/lifetime. Native pool misses and trimming remain normal.
- **Next pooled JSON array reads.** Under the built-in trusted default and UTF-8/UTF-16 length and token profiles, the shared contiguous formatter may decode a replacement `T[]`, a non-string `ImmutableArray<T>` or a default `ImmutableArray<string>` in one pass into exclusive pooled storage. It checks the closing array token at the enclosing depth, then publishes an exact-length result, and returns rented buffers with reference slots cleared. A valid prefix can invoke element callbacks before malformed later input is reported. Existing exact-type, same-length `T[]` targets are counted and validated before their slots are reused. Strict and custom profiles retain their existing full lookahead in this formatter. Nondefault immutable string arrays keep the prior string references as element read seeds.
- **Binary queue and heap windows.** A queue reader may consume the three storage words together after validating the full range, with individual reads for a truncated header. An exact priority queue using validated heap storage may write each fixed UTF-16 string and unmanaged pair under one capacity proof. It captures the whole pair before output and checks the mutation version at each enumeration boundary, including the final one. Unsupported profiles and layouts use public enumeration, and short output windows use the original scalar writes.
- **Rectangular JSON shapes.** Generated readers may hold the fixed-rank dimension and lower-bound buffers in stack storage. Once the complete shape and staged item count are validated, zero-based arrays may use the statically typed constructor. Nonzero lower bounds use the framework constructor with the original lengths and bounds.
- **Next concrete set formatters.** Fixed callback-free hash-set reads may validate the full payload and load entries while linking their buckets in wire order. Frozen set reads may feed the same validated input directly to the private builder, where normal insertion handles duplicates. Frozen set writes may batch compatible elements from the immutable item span. Exact integer sorted sets may write UTF-8 JSON through their validated tree, checking the version after each element. Reads into an exact default-comparer integer sorted set may build from a strictly ascending staged prefix; malformed input publishes the completed prefix through ordinary insertion, and unordered or duplicate input resumes ordinary insertion in input order. Derived sets, unsupported profiles and unavailable storage bindings retain their existing paths.
- **Reused hash sets.** Next binary reads of `HashSet<T>`, and of `ISet<T>` or `IReadOnlySet<T>` holding an exact `HashSet<T>`, clear an existing exact default-comparer set, ensure its capacity and refill its retained entries and buckets through the existing direct entry readers. Custom comparers and derived sets keep replacement, because the direct readers do not remove items that a different equality would merge.
- **One-pass linked lists.** Next binary reads of `LinkedList<string>` and generated object elements into a fresh or cleared list of the exact type may create each node with the public constructor right after decoding its element and link it through the probed node fields. The list publishes the head, count and version once after the last element, so a failed read leaves it empty as the staged fill does. Other lists, raw elements and unavailable probes keep the staged `FillLinkedList` path.
- **Typed binary sorted-set construction.** On x64 .NET 10 and 11 with compiled dynamic code, the verified sorted-tree builder may emit a typed call to the actual framework node constructor for non-string reference elements. The input range is checked before the emitted byref loads. The per-type probe must match the framework tree's node type, shape and colors. The existing comparer checks, staging, node topology and root, count and version publication still apply. Other platforms, unavailable runtime bindings and failed probes use the existing construction path.
- **Construction, pooling and reuse.** Constructor selection, `[LuminPackPoolRent]`, `ref` reuse of objects, collections and strings, and the documented publication rules on failure are preserved. Reuse is not transactional.
- **Reuse cache ownership.** Shared pool storage is bounded and unordered, with an atomic first slot and bounded hinted overflow scans. Only slot atomics transfer ownership; hints and diagnostic snapshots do not. Retain the existing thread-local fast caches and pool identity checks, reset before publication, dispose rejected items, and keep zero shared capacity distinct from disabling TLS. Object-pool resizing requires quiescence, publishes replacement storage before excess-item disposal, and aggregates disposal failures after draining. Local clearing detaches ownership before invoking disposal callbacks.
- **Binary string matrices.** After all dimension and count checks, the framework's default UTF-16 length profile may reuse an existing zero-based `string[,]` of the exact incoming shape. Read row-major slots with per-string bounds and configured quotas. Equal strings keep their references. Aliases observe each completed slot, including the decoded prefix on failure. Other profiles, shapes, ranks and runtimes missing the slot helper use their existing readers.
- **Binary object matrix slot reuse.** On .NET 8 and later, Next passes each slot of an existing rank-two array to its element's ordinary reuse reader unless the element declaration sets `ReuseRectangularArraySlots = false`. The target must have the exact runtime array type, incoming dimensions and two zero lower bounds. As with single-dimensional arrays and lists, slots sharing one element object observe the last record read into it. Shape and count checks precede mutation. Reads follow row-major order and can expose a decoded prefix on failure. Other targets use replacement reads.
- **Binary reuse of raw rank-two arrays.** On 64-bit modern .NET, an existing zero-based array with an eligible raw scalar element may supply the checked shape proof. Validate the entire retained input window, the nonnull marker, both dimensions and the explicit count against the same destination before moving the cursor. Reuse the existing block transfer. A failed proof starts the original checked reader at its original cursor, preserving destination publication and the failure position.
- **Portable BitArray storage.** Validated integer or byte backing storage may be written directly while preserving the runtime's public `CopyTo` padding behavior without mutating the input. Portable binary reads may fill an unpublished, word-rounded final `BitArray`, then apply the original public length adjustment and publish after success. Empty and extreme lengths, retained-capacity write fallbacks, payload validation and missing-API or unknown-layout fallbacks retain their established behavior. Modern target reuse and both JSON representations are unchanged.
- **Immutable tree JSON writes.** A concrete `ImmutableList<T>`, `ImmutableSortedSet<T>` or `ImmutableSortedDictionary<TKey, TValue>`, including an exact framework list reached through `IImmutableList<T>`, may copy its nonempty contents in enumeration order into an exclusive array lease. The writer calls the compiled formatters in that order and clears reference-bearing leases on return, including after an exception. Missing copy overloads retain direct enumeration. Unrecognized node layouts use public enumeration to fill the lease.
- **Raw immutable collection records.** A concrete `ImmutableList<T>` may copy its validated tree directly into a proven writable span for raw elements. Short output windows, unrecognized layouts and targets without the required unaligned stores use the staged writer. A raw `ImmutableStack<T>` may build its nodes by reading backward from the input after validating the complete payload, then publish the completed stack.
- **Framework immutable queue writes.** Binary and JSON may traverse the validated front and back stacks of an exact `ImmutableQueue<T>`, including one reached through `IImmutableQueue<T>`. Existing reversal caches are reused; an uncached back stack is traversed through a returned, reference-cleared pool lease without populating the BCL lazy cache. Empty and singleton backs need no lease. Element order, formatter calls, framing and failure behavior remain unchanged. Unknown layouts, missing helper APIs and arbitrary interface implementations retain their original traversal.
- **Concurrent collection traversal.** Stack writes may walk a validated immutable node chain captured at enumeration creation. Dictionary writes may use validated value traversal with lazy bucket capture, acquire reads, complete pair copies and the runtime's observed before/after-yield link timing. Missing metadata or helper APIs retain public enumeration. Bag writes retain the global/local freeze protocol and public snapshot order: raw unmanaged binary payloads may copy directly into reserved output; other binary and JSON paths return a complete pool lease and release locks before formatter calls. Unknown layouts retain `ToArray`; native `ArrayPool.Shared` ownership and trimming remain unchanged.
- **Concurrent scalar record kernels.** A Next binary writer for a concurrent dictionary with a string key and direct unmanaged value may prove room for the fixed UTF-16 key's upper bound and the value together, then use the original scalar stores and advance once. Other profiles and insufficient room use the original counted writes. Next JSON concurrent sequences and dictionaries may use the runtime's complete integer element or pair writers for matching framework scalars. These kernels preserve the existing traversal, wire framing, callbacks, validation and fallback when the runtime operations are unavailable.
- **Collection dispatch.** Select collection traversal and construction using storage layout, formatter capabilities and callback behavior. A benchmark key/value type combination must never select a separate algorithm. Generated JSON dictionaries frame every entry as an array and dispatch each component through its formatter. Existing generated assemblies retain their callable runtime signatures. On supported modern targets, an exact binary dictionary with its default comparer can refill existing slots when its fixed-width key uses callback-free framework equality and the value formatter supports safe in-place reading. Matching keys retain the destination order. A failed read can expose the completed prefix. User-defined key behavior, custom comparers and unsupported value formatters use staged reconstruction. Empty destinations with callback-free keys can use the checked bulk rebuild for raw pairs.
- **Shared unmanaged roots.** Closed formatter roots of one generic definition or array rank whose bodies differ only in unmanaged type arguments may be emitted once as a generic root constrained to `unmanaged`. Each closed root keeps its name, signature and `Preserve` attribute and becomes an aggressively inlined forwarder; the generic root keeps the original inlining attributes. A root is shared only when substituting each member's arguments reproduces the member's body and every expression of the generic body binds to the same definitions, types and constants as the member's own body, without errors. `Nullable<T>` and members that fail either proof keep their closed roots. Value-type instantiations remain separately compiled by CoreCLR, NativeAOT and the default IL2CPP setting; IL2CPP's full generic sharing (the "Faster (smaller) builds" option) may run them through shared code.
- **Fresh binary concurrent dictionaries.** On validated .NET 10 and 11 x64 layouts, a fresh `ConcurrentDictionary<TKey,TValue>` with at least 32 staged pairs may fill vacant buckets and update their per-lock counts before publication. Hash each key once with the comparer held by the current table. Delegate occupied buckets and growth to the framework insertion routine with that hash, and refresh the table after rehashing. Preserve the constructor's duplicate filter, first-value replay, key callbacks and null-key failures. Use framework construction on unsupported layouts. Existing targets use their own comparer and insertion path.
- **Fresh binary concurrent bags.** On probed .NET 10 and 11 x64 layouts, a newly created exact `ConcurrentBag<T>` with 64 through 4096 staged items may presize the local work-stealing array after the first ordinary `Add`. Hold the existing global and local freeze locks and require the single initial queue, its owner thread, original capacity and first-item indices. Preserve publication, input order, counts and the remaining `Add` operations. Replacement through a callback or an unrecognized queue uses ordinary insertion.
- **Reused concurrent queues.** Next binary and JSON reads empty a reused `ConcurrentQueue<T>` of any element with framework dequeues when Core exposes `DrainConcurrentQueue`, so the refill reuses the retained tail segment instead of a new growth chain. Existing snapshots keep their captured segments and each removal keeps the framework's concurrency guarantees. Without the helper, raw scalars keep the sized `TryClearConcurrentQueue` reset below and other elements use `Clear`.
- **Binary raw concurrent queue reuse.** After validating the full raw payload, Next may clear an exact `ConcurrentQueue<T>` of supported scalars with `TryClearConcurrentQueue` for 33 through 4,096 elements. ### Options and generation

- **Compile-time options.** `[LuminPackOption]` scopes (assembly, type, member) and stateless `ILuminPackOptions` profiles are compiled in. There is no runtime options object or mutable global default. JSON encoding, depth and syntax policy apply to a whole document, selected by its root.
- **`UntrustedData`** selects checked binary reads at compile time and is on by default; `UntrustedData = false` generates exactly the trusted code. Untrusted records use the ordinary wire format and writers. Generated reads of objects, version-tolerant records, reference-tracked records and Unions check object markers, Boolean domains, back-reference types, raw slot widths, compressed counts and declared collection and string limits at the actual read sites, with the root's limits frozen as constants; undeclared limits are unbounded constants. Depth is counted only in recursive types with a declared `MaxDepth`; Reader bounds and stack guards stay on. An explicit hostile-input declaration also selects the strict JSON profile. Input-selected types fail closed. There is no envelope, ambient accounting state or schema prepass.
- **`[LuminPackBounded]`** is a caller guarantee: the bounded record reserves once and drops inner container checks.
- **Automatic generation** discovers declared model graphs and statically required closed operations. Legacy generation-mode settings are ignored. Applications and Unity's predefined assemblies without friend access retain each operation independently for the payloads reached from its bound calls, including their member graphs and Union dependencies. Compiler interception and IL rewriting use the same operation selection. Unresolved serializer expressions, registration and direct generated formatter calls retain all four when the call graph cannot establish a narrower requirement. Libraries retain all four for their discovered payloads because consumer calls are outside the compilation. Registration and wire semantics are independent of this selection. Assembly-level generation options can force retention of an individual operation.
- **Incremental caches** keep exact semantic dependencies, settings, diagnostics and deterministic identities. No `Compilation`, `SemanticModel` or symbol may survive in a cross-compilation cache. Retained-driver output must equal fresh output.

### Optional modules

- Core references neither `LuminPack.Unity` nor `LuminPack.Burst`.
- The `LuminPackBurst` hook table exists only for `netstandard2.1` and follows the [hook ABI](burst-hooks.md). Null slots keep the Core implementation. Burst code is projected from Core sources, never maintained as a second algorithm.

## 3. Safety rules

1. **Reader checks stay on in Release.** The advancing Reader's public `EnsureReadable` and its callers (`Advance`, fixed storage batches, Union framing) are active in every configuration. Do not restore `Conditional("DEBUG")`, wrap checks in `#if DEBUG`, or bypass them for performance.
2. **Check before access.** Generated cursor arithmetic that replaces `Advance` keeps its range check before moving the cursor. Scalar reads and fixed-field fallbacks validate the complete range before any unsafe load or destination write.
3. **Dynamic checks stay.** Collection, string and bulk-payload header and payload validation is mandatory. A count is validated against the remaining input before any allocation sized from it.
4. **Separate unchecked contracts.** Fixed Writer stores into reserved room and address-only raw kernels keep their existing unchecked contracts. This does not permit removing Reader checks or adding blanket Writer checks.
5. **Recursion.** Operations of recursive payloads call `EnsureSufficientStack`, and recursive binary writes check capacity on re-entry.
6. **Signed comparisons.** Range checks against cached ends use signed 64-bit distances so a cursor past the end and negative counts are rejected on every target.
7. **Exceptions** are thrown through `LuminPackExceptionHelper` (runtime) or the generator's own helper. Keep exception types, argument names, cleanup and original stacks.

## 4. SIMD

- Review scalar, 128-bit, 256-bit, 512-bit and ARM64 execution for every SIMD change.
- Guard every ISA-specific operation by its exact required features. Width preference is not hardware support.
- Keep bounded tails, a scalar or portable fallback, zero-length behavior and identical bytes. Never read or write outside a complete validated range.
- A fixed-width algorithm may keep its natural width only with a documented reason.
- Hardware unavailable locally requires CI execution. Compilation or synthetic masks are not hardware validation.

## 5. Performance evidence

- The primary evidence is LuminPack's elapsed time divided by the reference library's, measured on the same machine, fixture, runtime and options, in the same run. Lower is better.
- Report before/after ratios against the same references, repeated samples with dispersion, and allocations. Keep absolute times as supporting evidence.
- Do not infer a win from one nanosecond figure, and do not assume all workloads fluctuate together.
- When machine load makes timing unreliable, compare retained IL and native code instead, and say so.
- Benchmarks of reusable buffers include the reset of each independent record.
