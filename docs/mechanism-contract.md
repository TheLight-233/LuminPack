# Mechanism contract

[Chinese](mechanism-contract.cn.md)

This document lists the hard constraints of LuminPack. It applies to the whole repository: runtime code, the generator, generated code, optional modules and conditional targets. A passing round trip, a smaller file or a faster benchmark is never a reason to replace one of these mechanisms on its own.

The history of individual approvals lives in Git. When this document, the code and the history disagree, report the discrepancy with evidence instead of silently picking a design.

## 1. Change control

1. **Mechanisms are preserved by default.** Every mechanism in section 2 stays as it is unless the owner explicitly approves a concrete replacement.
2. **Experiments come first.** A faster alternative is prepared in `experiments/` (kept out of version control), with:
   - before/after elapsed-time ratios against the same reference libraries (for example Nino, MemoryPack, System.Text.Json), measured on the same machine, fixture, runtime and options, in the same run;
   - repeated samples with their dispersion, and allocations;
   - generated source, IL or native code where it matters;
   - the semantic, API, wire, ownership and platform trade-offs.
3. **Only explicit approval of that concrete proposal authorizes the replacement.** A performance target, a refactoring, dead-code removal or a size reduction is not approval.
4. **Correctness fixes are distinct.** A reproduced bug may be fixed while keeping the intended protocol. Record it as a fix with its regression test, not as an unchanged implementation.
5. **Approved differences are recorded.** Add the approved rule to this document (not a dated narrative) and describe the change in the commit.
6. **Commit completed work by default.** After completing a feature or fix and its relevant verification, commit only the task's changes using the [commit conventions](../CONTRIBUTING.md#commit-conventions), without asking for commit permission. Exclude unrelated or unfinished changes. Ask whether to push after committing unless the owner has already authorized that push. Tags and published-history rewrites still require explicit authorization.

## 2. Preserved mechanisms

### Storage access

- Ordinary binary class records use the generator’s inlining budgets even when they contain nested objects, unions or collections. Eligible small record bodies receive `AggressiveInlining`. Other record bodies leave the decision to the JIT. Collection loop methods and cold helpers keep their explicit non-inlining boundaries. Reference-tracked objects keep the call boundaries in their root read and write paths. Scalar stores and loads use Core’s `Write`, `WriteReserved` and `Read` helpers. Core obtains a supported dictionary view, native input span or record window for each storage operation. Generated field copies prove each adjacent offset and use scalar access when the proof fails.

- **Local + As views.** Private, protected, readonly and auto-property backing storage is accessed through generated layout mirrors and `Unsafe.As`, never reflection. Mirrors replicate the inheritance chain and `LayoutKind` (including explicit offsets). Accessible writable fields are accessed directly.
- **Storage placeholders.** Mirror fields, padding members and hidden storage must not be removed because ordinary call-site searches find no use.
- **Adjacent-field bulk copies.** Consecutive unmanaged fields may be copied as one block only on 64-bit, after proving the actual field addresses match the packed offsets, excluding volatile fields, and keeping a field-wise fallback.
- **Architecture-specific fixed access.** On 32-bit, an individual unmanaged value with `Unsafe.SizeOf<T>() <= 4` may use typed `Unsafe.ReadUnaligned` / `WriteUnaligned`. Larger values and field batches use `LuminPackMarshal.CopyBlockUnaligned` and the packed storage views, because typed unaligned access of those can crash IL2CPP. All members being four bytes or smaller does not permit a typed aggregate access. On 64-bit, typed access and block copies are both allowed.
- **Raw copies.** Non-overlapping block copies, including generated ones, go through `LuminPackMarshal.CopyBlockUnaligned`; only that helper calls `Unsafe.CopyBlockUnaligned`. Overlap-safe span copies keep memmove semantics. Its per-processor size ranges (Intel, AMD Zen 5, other AMD and other x64, read once from CPUID; runtime copy on other targets) change only with new cross-host measurements recorded beside `LuminKernelPolicy`; the zeroed-array thresholds of `AllocateUninitializedArray` (16 KiB on Intel, 5 KiB elsewhere) follow the same rule.

### Representations

- **Object mode** is positional with a one-byte member count (0 to 249, `255` = null).
- **Version tolerance** uses descriptor tables and scoped schema registration. Full revision 4 records convey the schema hash and ordered name-key, type-contract and width descriptors. Revision 5 uses an ordinal in the active registration table. `LuminPackOldName` preserves the oldest key on write. Width 254 follows the record's string framing. Width 255 uses a four-byte length and a nested registration scope, which is truncated at the end of the member. Revision 1 reads remain available in a cold decoder.
- **Reference tracking** is selected through `TrackReferences` on a concrete class. The established null marker, explicit id and compact back reference remain. After the first-occurrence header, the selected Object or VersionTolerant format supplies the body. Writers start with a short identity scan before hashing. Readers store reference ids in an indexed table and keep early shell registration and the reuse probe.
- Binary reference roots check the reference marker before entering the record body. Positive writes register the identity once and repeated writes reserve the marker and the complete id together. For ids from 0 to 127, Core writes the two reserved bytes in one little-endian 16-bit store and advances once. Larger ids use the outlined writer with the existing variable-length encoding. The read consumes the existing tagged id and validates its registered type. Callback, stack and projected input checks retain their original ordering.
- **Unmanaged struct layout selection.** Next honors type-owned `StructLayout` declarations. Values that cannot carry a type-level `LuminPackOption`, including framework and external non-LuminPackable values without their own contract, follow the consuming project's assembly option. The default is `Tagged`.
- **Tagged** keeps the native block-copy path while supporting readers with other layouts. A proven single-layout block or individual value uses headerless native bytes. An individually formatted multi-model value uses packed field order and omits the tag. A multi-model collection block writes the tag identified by its verified local stride and field offsets and copies the native bytes. A reader with the matching layout copies the validated block. Other layouts convert the validated bytes through the existing SIMD or scalar layout kernel. Preserve overlapping matching-layout reads with memmove semantics and stage overlapping inputs before conversion. An unmodeled writer uses the canonical model. Add models without changing existing tag meanings. Element-wise containers retain their framing.
- **Packed** gives supported values a portable representation in storage declaration order without padding. A Packed field propagates packed storage through enclosing structs, framework key/value pairs and value tuples. An explicit `Native` declaration establishes a storage boundary. A Packed block may copy its raw storage when actual field offsets and stride prove that it already matches the packed representation.
- **Native** moves the full host storage, including padding, for callers that require native representation on endpoints with identical layouts. Its blocks omit layout tags and conversion.
- **Strings** default to fixed-width UTF-16 length records, with the compact Latin-1 form; UTF-8 and token profiles stay available. Opt-in `VarInt` recording encodes each existing length header plus one as canonical unsigned base-128, preserving payload encodings and distinct null and empty records. UTF-8 keeps both length fields. Fixed-width defaults and their wire bytes remain unchanged; both endpoints select the same profile. Token records share the empty terminator.
- **JSON** keeps its envelopes (`$type`/`$value`, `$id`/`$ref`, `Lazy`, multidimensional arrays) and rejects non-finite numbers.
- **Canonical JSON clock reads.** On modern .NET, the built-in UTF-16 length profile can parse the exact `HH:mm:ss.fffffff` token for `TimeOnly` and nonnegative sub-day `TimeSpan` under invariant current culture. The reader validates and snapshots the token and completes the value before the bounded digit checks and construction. Other forms, cultures and profiles use the existing parser.
- **Canonical JSON date reads.** Modern Core may parse the exact invariant `yyyy-MM-dd` form of an already decoded `DateOnly` token with bounded ASCII digit and Gregorian calendar checks. Next selects the helper when the referenced runtime exposes it. Keep the existing token completion and fallback to the framework round-trip parser for other forms and invalid dates.
- **Canonical JSON timestamp reads.** On modern .NET, the built-in UTF-16 length profile under invariant current culture may parse the exact round-trip `DateTime` form with a UTC marker and the `DateTimeOffset` form with an explicit signed offset. After existing validation, private token capture and value completion, narrow the bounded ASCII token and require the framework round-trip byte parser to consume it in full. Other forms, cultures and profiles use the original parser.
- **Reference-tracked JSON property heads.** On 64-bit modern .NET, generated writers may copy a complete static property head into the current window and advance once for both contiguous and segmented output. The head uses the document encoding and the current separator state. A short window or an unsupported profile uses the original property writer, preserving output callbacks, committed prefixes and reference registration order.
- **Ordinary JSON integer runs.** For consecutive directly writable, nonvolatile `Int32` fields, the generated reader may match complete static heads and decode plain integers in a bounded local managed window. Publish only the successfully consumed prefix at a chunk boundary or before falling back. Preserve per-field publication, separator grammar, reuse, and the ordinary parser at the first unmatched field.
- **Byte order** is little-endian. No mode performs endian conversion.
- **Compression** uses `LUM2` frames with single-byte length extensions below 255 and an escaped canonical unsigned base-128 remainder for longer lengths, a 64 KiB match window and the per-thread position table. High-ratio allocating reads validate complete sequence structure before allocation. Earlier `LUMZ` frames are rejected. Match hooks, bounded SIMD tails, decoder checks and 32-bit access rules remain in force; see [compression](compression.md).
- Changing any wire byte needs explicit approval and updated wire fixtures.
- **Binary system time zones.** A recognized catalog instance can carry its identifier after marker `1`; the null marker and complete snapshot marker `0` retain their established meanings. Catalog eligibility uses reference identity. The receiving catalog provides the system rules, and a missing identifier fails before publishing the destination. The selected string profile and input limits apply to the identifier. For built-in UTF-16 length UTC output, a single fixed write requires enough space for the complete record before the growth threshold. Short windows use the original framed string operations.

### Dispatch

- **Named member kernels.** Source-owned, non-generic positional classes without inheritance, callbacks or bounded-record declarations may share a concrete static member writer when their members are public raw storage or strings and at least one member is a string. Purely fixed records keep their existing compact stores. Preserve the original member header, field-address proofs, fixed stores, string operations and compiled member profiles; do not replace them with the standalone root's capacity fusion. Member kernels retain an inline hint, while their callers leave root inlining to the runtime. Complete public-field writes consisting only of runtime record kernels and unscoped named member calls may lower directly from existing type facts. All other contracts retain their existing operation projection. This adds no runtime plan, formatter witness or payload dispatch and removes no existing entry.
- **Next nested record entries.** JSON nested fields use the concrete formatter's document-profile entry. A positional binary child may use its existing object or payload read only where it preserves the original header, checked-input policy, field-address proofs and partial-read behavior. Stage the child locally so a newly allocated instance is published only after a successful member read. Existing binary member writers and standalone writers with equivalent stores may be called directly. Preserve the original member write where the standalone entry reserves output differently.
- **Static entries** use compiler interceptors when versioned interception locations and C# 11 or later are available. Closed payload calls, including explicit generic syntax, bind the existing concrete roots without payload dispatch, reflection or delegate caches. Explicit profiles use both payload and profile type arguments; no backend emits payload-specific profile convenience overloads on the public facade. Concrete state forwarders have payload-specific names on statically integrated paths; convenience entries live in payload-specific containers. No new runtime plan or formatter witness is introduced. Older compilers use the installed IL postprocessor with the same generated entries and exact signature mappings. It substitutes local static call operands, validates stack types, preserves portable symbols and requires the original signing key for signed images. When both integrations are disabled, default calls retain concrete overloads and explicit profiles use registered generic fallback.
- **Internal state forwarding in applications.** In executable projects with compiler interception and without friend access, an exact single-call state interceptor may call its existing nested root directly. Its signature, profile and passing conventions stay intact. A payload-specific internal forwarder may be omitted only when the completed contributions and consumer source leave it without a reference and its declaration is unambiguous. Libraries, friend assemblies and the IL rewriting backend retain their state forwarders and binding contracts.
- **Source generic wrappers** may be specialized at closed calls when their static source bodies can be relocated safely. Preserve argument evaluation, overload selection, caller information, side effects and correlated method/enclosing-type arguments. Opaque or unsupported bodies keep the original call and registered fallback. Interception never rewrites referenced assemblies or virtual dispatch.
- **Next static entries.** Next intercepts only facade calls with a closed payload. Each interceptor calls the existing static root and implements its required document boundary. Explicit profiles share the interceptor's profile type parameter. Open payload calls in source generic wrappers use registered fallback without interprocedural expansion. Generated XML documents the public facade.
- **Generic fallback entry points** serve explicit and `Custom` registrations. Next also publishes the emitted operations of discovered closed payloads in a consuming-assembly table and uses Core-owned built-in scalar and string registrations. The facade initializes these registrations on first use, and explicit operations take precedence. Missing registrations or operations throw `LuminPackException`. Disabling registration disables the fallback. No runtime type discovery or reflection factory is used. Fallback document boundaries use the consuming assembly defaults or the explicit profile, while intercepted concrete roots keep declaration-owned options. A generic spelling alone no longer requests registered dispatch when its payload can be intercepted.
- **Union dispatch.** Next writes class and interface Unions with up to 32 generated cases through an exact runtime type comparison chain and calls each concrete payload writer directly, including closed and open generic cases. Each binary exact-dispatch branch calls `GetType()` in the comparison with `typeof(Case)`. Larger Unions retain the generated public virtual slots. A virtual generic writer that selects among declared cases caches the matching case-name hash as a `static readonly int` for each closed type. Its second dispatch uses the same hash constants in both formats. JSON still writes the declared numeric tag. Only the virtual tier requires partial declarations for slot injection. An unmatched type keeps the typed registration lookup or the unknown-case error. Binary exact writers with registration put that fallback in a non-inlined helper.
- **Binary Union case names.** Next encodes a generated case as a little-endian four-byte FNV-1a hash of its canonical UTF-8 type name, followed by its existing payload. Names include namespaces, nesting, closed generic arguments and positional open parameters. The generator rejects collisions and reserved values. Zero encodes null. All ones precedes the existing registered delegate's numeric tag and payload. JSON and C# compiler Union structs retain their existing tags. The previous binary class and interface Union frame is a different wire schema.
- **Union collections.** Lists, single-dimensional arrays, `ImmutableArray<T>` and dictionaries use the root's write tier for each element in input order. Dense dictionary writers apply that same tier within their existing fixed Union cursor protocol. Payload width does not change the tier or string representation. Binary state forwarders for Union members retain their inline hint and call the original root.
- **Fresh Union elements.** Newly allocated Union collection storage may read through a zero-initialized local before assigning the element, preserving the Union operation's existing publication after successful payload reading. Existing elements retain their reuse path; ordinary objects and Custom formatters retain their own publication contracts.
- **Fresh fixed Union reads.** Next may use the existing checked block reader for an allocated, non-pooled fixed case on a 64-bit modern target. The case has no callbacks and the run has directly writable, nonvolatile, unmanaged fields without Boolean validation. Prove the actual field addresses before using the block and keep the field-wise fallback. A reused exact case may use the same checked block, because the complete run is validated before any byte is copied; the reuse arms store the slot only when the case object changes. Validate the full input before moving the cursor or writing the batch, and publish the new case only after the payload succeeds.
- **Fresh payload record batches.** A record root's payload-framing read may use the object read's proven checked batch (`ReadBatch` or the checked block read, with field-address proofs and the field-wise fallback) for a fixed run of directly writable, nonvolatile fields when it has just created the instance. Records with callbacks or pooled rentals and reused instances keep the field-wise read. Callers stage the new instance in a local, except the public polymorphic read slot, where an invalid Boolean byte now leaves the copied run in the published instance, as the object read already does.
- **Shared fixed Union block reads.** A Union read switch may let two or more fixed cases with the same payload width share one checked block read. Each case keeps its own allocation or exact-type reuse, field-address proof and field-wise fallback; a proven case selects its destination block and jumps to the shared read. A fresh element is published only after that read, and a reused destination is stored after it only when the case object changes. The switch handles the four-byte null marker and checks the discriminator before reading a payload.
- **Registration** passes typed delegates (`LuminPackFormatter`) without requiring an unsafe context. Conditional weak tables retain complete registrations for the payload type's lifetime; MethodTable indexes hold weak references, allowing collectible payload assemblies to unload. Delegates and captured targets remain alive while their payload registration is alive. Registering collectible code for a noncollectible payload retains that code for the payload's lifetime. Registration validates tags, case types and required operations before publishing.
- **`Custom`** formatters own their complete representation and are invoked through their registered delegates.

### Execution state

- **Advancing cursors.** Binary and JSON readers and writers use a `ref byte` cursor on modern .NET and a one-element `Span<byte>` to carry the managed cursor address on `netstandard2.1`. The span length describes the cursor representation. The retained window and cached end define the accessible range. Low-level callers can get the cursor reference through `MemoryMarshal.GetReference`.
- **Cached ends.** Writer, Reader, JSON Writer and JSON Reader cache the end of their window (or the writer's growth threshold) beside the cursor. `Buffer`, `BufferCheckLimit` and `Owner` have public getters and internal setters that refresh the cache; every constructor and window change must refresh it.
- On modern 64-bit .NET, checked scalar and collection reads validate the distance to the cached end against the full window, including cursors before its start. Writers use the cached record limit for requests inside the window and consult physical capacity past the threshold.
- **Cursor publication.** Generated code may keep the cursor in a local between state-observing boundaries. It must publish the cursor before calling a formatter, a Union or recursive operation, a callback, or a capacity check, and resume from the resulting state afterwards. Never keep a buffer reference across a resize.
- **Object marker and first scalar.** A modern plain positional class can write its member count and one leading scalar with a single cursor update when its next field uses a variable-width formatter. This requires a directly accessible nonvolatile field, a compatible Core, and a class without base payload, implemented interfaces, callbacks, mirrors or an explicit size bound. Consecutive fixed fields keep their existing layout proof. The scalar uses the standard 32-bit storage rules and Debug validates the two advances in order.
- **Scalar reads.** Generated scalar loads call `LuminPackReader.Read`. A fixed batch or a sequence window may use the address-based overload after validating the entire range. The Reader owns the 32-bit scalar access decision. Storage proofs and validation for batched and untrusted reads still apply.
- **Fixed Union case writes.** An eligible local non-generic class Union can write its four-byte hash and callback-free fixed payload in the shared cursor-returning body. On the managed-reference path, combine the tag and payload advances as an offset from the current output reference. Resolve the offset before returning and before a capacity reservation, then restart the offset from the refreshed cursor after the reservation. The virtual tier keeps its profile-specific slots. External-input policy cases retain the ordinary checked path.
- **Large fixed Union records.** Fixed payloads whose width plus the maximum Union header exceeds the ordinary minimum growth headroom reserve their complete payload before its unchecked stores. The returning body publishes its absolute cursor before that capacity boundary and reacquires output storage after growth. Small fixed payloads keep their threshold-based reservation contract.
- **One state body per operation.** Each retained type has one complete body for each operation that is generated (binary write, binary read, JSON write, JSON read; see automatic generation); convenience overloads forward to it. Direct records also keep one exact-width body for their allocating write. A wide binary writer may reuse a closed framework collection writer for repeated compound-element traversals outside loops and capacity reservations. It passes the original state and compiled member profile. Exceptionally wide binary readers may split complete member branches into static local functions that share the original reader by reference and act on the same class instance. Validation, cursor movement and publication on failure keep their original order.
- **Managed output storage.** `LuminBufferWriter` owns one `ArrayPool<byte>.Shared` array. On every target a `GCHandle` pins each newly rented array before the writer measures its 64-byte alignment offset. It stays pinned until return, preserving the alignment across GC. Growth keeps the 32 KiB initial capacity, 1.5x growth and 87.5% threshold. It extends in place while the array fits or copies to a newly pinned array before unpinning and returning the previous array, then refreshes the cursor and end caches. The owner clears or writes every exposed byte. A finalizer frees the pin of an abandoned rental. Explicit disposal or return can recycle the array.
- **Caller-owned append sessions.** Overloads taking a `LuminBufferWriter` append at its cursor and retain the current operation state. `Reset()` clears the published byte count, live cursor, and writer and reader operation states while retaining capacity. `ResetWrittenCount()` clears the count and cursor while retaining both states and capacity. `ResetAndRelease()` performs a full reset and returns any current array rental. The writer stays usable.
- **Fixed object records.** Callback-free fixed native class records may reserve their existing positional header and all fields together and publish the cursor once. Only proven adjacent fields may be copied as a block. A counted array can share the capacity check for consecutive nonnull fixed records when the current room covers their complete bounds; nulls and insufficient room retain the ordinary record path.
- **Raw positional and versioned members.** Eligible raw arrays and framework lists can reserve their collection payload together with adjacent record fields. This binary capture decision is independent of publishing formatter owners for other operations. Reads retain the checked owners, and collection markers and element bytes keep their existing encoding.
- **Exact version member widths.** Widths 0–250 encode a proved fixed payload width. A fixed-width nullable member reserves the same width for null and present values. Other payloads use their record string codec or a bounded length block and backpatch. Readers validate the range before a fixed load and validate the end of every decoded length block.
- **Version descriptor emission.** The writer copies the generated descriptor bytes in one unaligned block after reserving the full header. The short header writes only the marker, form and ordinal. The reader confirms descriptor bytes before using the model's positional path. Both forms retain input checks and the compiled profile stamp.
- **Profile observation order.** A generated positional or versioned write may move a newly captured raw collection into an earlier reservation under verified built-in profiles. Other profiles use the original reservation boundaries when a profile property can run before the collection is observed.
- **Independent default reference contexts.** Separate default readers and writers never share reference identities.
- **Fresh JSON sequence capacity.** Fresh List/Queue storage, ordinary sequence interfaces, Collection/ObservableCollection and their read-only wrappers may use a read-only structural capacity hint before their original element loop. Grouping/Lookup element lists share that rule. Existing targets keep their original reuse/publication and callbacks; unavailable hints or later count changes keep growth fallback. Tiny inputs skip sizing. Fresh Capacity may change and the extra scan may cost CPU; avoiding growth allocations has priority. Arrays and dictionaries retain their original construction paths; optional-helper metadata is checked before emission.
- **Fresh JSON hash-set capacity.** On modern .NET outside Unity, a fresh concrete `HashSet<int>`, `HashSet<long>` or `HashSet<string>` can use the existing structural hint for the built-in default and UTF-8/UTF-16 length profiles. The probe starts at 128 elements and preallocates only when the hint is at most 4,096. The ordinary insertion loop still reads every element and handles duplicate or invalid input. Existing sets retain their comparer and clear behavior.
- **Next ObjectModel wrapper formatters.** Exact framework wrappers over known lists or arrays, and the sealed collection builder, may batch UTF-16 length strings and UTF-8 JSON integers through the existing span kernels. Versioned storage checks its enumeration version across output boundaries and reloads the backing array after capacity changes. Other storage and profiles use the original formatter loop. JSON observable insertion checks exact type and listener state after each element formatter. A capacity hint may size fresh wrapper or builder storage before the original element loop.
- **Next collection interface writes.** Exact framework lists, arrays, sets and dictionaries may select their concrete traversal. The original interface enumeration remains available for derived and arbitrary implementations. Mutable dictionary interfaces may write each callback-free raw pair after one complete bounds check. The count is patched after enumeration, and the original per-member path handles short output windows. JSON may combine the separator and integer element or pair in the existing logical record. On modern .NET, the binary owned writer may use the legacy counted span and complete per-object reservation for exact List storage, built-in UTF-16 length profiles and callback-free positional records whose variable members are strings or raw scalar lists. Array and arbitrary interface implementations, custom profiles and span destinations keep their existing paths.
- **Next concrete map records.** In binary, a nonempty run of raw pairs in validated sorted-list arrays or a private sorted-dictionary lease may use one complete output check. The original scalar loop handles short windows. A fresh dictionary of fixed integer pairs may read directly into proven storage after validating the complete payload. JSON integer entries may combine framing with numeric writes. Exact sorted-list JSON traversal captures both members before writing either and checks the mutation version at each original enumeration boundary, including the final one. The bounded UTF-16 pair writers also recognize declaration-owned wrappers of the built-in UTF-16 length and default profiles. A dense binary dictionary with a raw key may omit the value formatter’s preliminary growth check when the whole key fits before the growth threshold. The boundary path checks capacity and captures the value before its original threshold operation. For an Int32 key and value, a built-in UTF-16 profile can emit both numbers and their pair delimiters into one complete output window. A short window or a culture with formatting callbacks keeps the ordinary scalar operations.
- **Concurrent integer and string pairs.** A concrete concurrent map with a signed or unsigned 32-bit or 64-bit integer key and a string value can hold the cursor for a complete pair under the built-in UTF-16 length profile. Both fields come from the same weakly consistent iterator item. One proof covers the native key and the full string bound before the current growth threshold. A shorter window publishes the prefix before the original scalar operations and then refreshes the cursor. The existing fixed-width stores enforce the platform alignment rules. Other profiles, external buffer publication and the observed count backpatch use their established paths.
- **Parallel dictionary storage.** Sorted-list and frozen dictionary binary writers may use one capacity proof per fixed UTF-16 string and unmanaged pair from validated parallel storage. The established scalar fallback retains key-before-value loading across output growth. JSON sorted-list traversal retains its version checks and value capture order.
- **Next contiguous collection runs.** Exact `int` and `long` spans may write JSON elements with a local cursor in the current output window. Short or overlapping windows and UTF-16 cultures with user callbacks use the original scalar operations and input-load order. Segmented UTF-16 length string writes may use the existing binary string-run kernels under both the storage bound and the original growth threshold. They keep the accumulated count backpatch and the scalar check at the next record boundary. Rectangular JSON arrays keep their shape envelope and copy the validated staging span into the result in row-major order. The storage address comes from the framework array-data API or the typed cell at the declared lower bounds on older targets.
- **Short raw collection writes.** The writer can inline the existing small-block kernel for a checked or reserved collection payload through 32 bytes on supported 64-bit targets. Wider and unsupported copies keep the normal copy policy and the shared unaligned helper.
- **Next mutable stack, queue and heap records.** Exact validated stacks may move reference-free binary storage in bottom-first order within a proven window and publish a direct refill only after the complete payload check. String stacks and wrapped string queues may use the checked UTF-16 length record runs. A failed staged string read leaves the stack empty and clears reference slots. UTF-8 integer stack and queue writers can format directly across output windows. They capture the current item before a separator or value can call the output owner and check the enumeration version before continuing, including after the final item. Priority queues keep heap enumeration order. A complete raw binary window can write the two fields without tuple padding, and a fixed scalar reader with the default comparer can accept a checked heap-order prefix before returning to ordinary insertion. On x64 with SSE and SSE2, packed pairs of a four-byte element and an `Int32` priority may check each group of four children against their shared parent with one vector comparison and copy the group; the scalar check resumes at the first rejected group. JSON can reuse the bounded integer entry writer and a capacity hint for large fresh heaps with string members while preserving existing comparers, entry grammar, partial-read publication and fallback operations.
- **Deep JSON lookahead storage.** CountArrayElements owns an independent deep-grammar copy, may rent/grow that private copy from ArrayPool<byte>.Shared, and returns it in finally on success or failure. The original reader storage and all state remain unchanged. Ordinary reader-owned deep grammar retains its original allocation/lifetime. Native pool misses and trimming remain normal.
- **Next pooled JSON array reads.** Under the built-in trusted default and UTF-8/UTF-16 length and token profiles, the shared contiguous formatter may decode a replacement `T[]`, a non-string `ImmutableArray<T>` or a default `ImmutableArray<string>` in one pass into exclusive pooled storage. It checks the closing array token at the enclosing depth, then publishes an exact-length result, and returns rented buffers with reference slots cleared. A valid prefix can invoke element callbacks before malformed later input is reported. Existing exact-type, same-length `T[]` targets are counted and validated before their slots are reused. Strict and custom profiles retain their existing full lookahead in this formatter. Nondefault immutable string arrays keep the prior string references as element read seeds.
- **Raw immutable array reads.** On .NET 8 and later, Next may read a raw scalar `ImmutableArray<T>` through the runtime checked reader. It validates the count and complete payload before allocating, copies into new array storage and advances the cursor after the copy. Default and empty values remain distinct. Boolean elements, older runtimes and unavailable APIs keep their existing paths.
- **Binary queue and heap windows.** A queue reader may consume the three storage words together after validating the full range, with individual reads for a truncated header. An exact priority queue using validated heap storage may write each fixed UTF-16 string and unmanaged pair under one capacity proof. It captures the whole pair before output and checks the mutation version at each enumeration boundary, including the final one. Unsupported profiles and layouts use public enumeration, and short output windows use the original scalar writes. For same-sized default-comparer string/Int32 heaps in a fixed UTF-16 length profile, reads can retain the prior element strings in a pooled array before clearing the destination. Each checked pair is enqueued immediately, so aliases see the completed prefix if the input ends early.
- **Rectangular JSON shapes.** Generated readers may hold the fixed-rank dimension and lower-bound buffers in stack storage. Once the complete shape and staged item count are validated, zero-based arrays may use the statically typed constructor. Nonzero lower bounds use the framework constructor with the original lengths and bounds.
- **Next concrete set formatters.** Fixed callback-free hash-set reads may validate the full payload and load entries while linking their buckets in wire order. Frozen set reads may feed the same validated input directly to the private builder, where normal insertion handles duplicates. Frozen set writes may batch compatible elements from the immutable item span. Exact integer sorted sets may write UTF-8 JSON through their validated tree, checking the version after each element. Reads into an exact default-comparer integer sorted set may build from a strictly ascending staged prefix; malformed input publishes the completed prefix through ordinary insertion, and unordered or duplicate input resumes ordinary insertion in input order. Derived sets, unsupported profiles and unavailable storage bindings retain their existing paths.
- **Reused hash sets.** Next binary reads of `HashSet<T>`, and of `ISet<T>` or `IReadOnlySet<T>` holding an exact `HashSet<T>`, clear an existing exact default-comparer set, ensure its capacity and refill its retained entries and buckets through the existing direct entry readers. The captured object is written with its original formatter after the key, preserving field observation, callbacks, version checks and collection backpatching.

The value must be eligible for the existing bounded mixed-record writer. That writer stores the captured pair when the full raw bound and growth threshold permit it. Other profiles, empty inputs and unsupported backing layouts keep the original wrapper path.

Each completed pair is immediately visible and the original version and failure behavior remain. The cache retains at most four cleared arrays. Checked projections with enclosing limits and unsupported shapes use the original reader.

Retained destinations keep their original clear and insertion behavior.
- **Allocating binary scalar list writes.** An eligible framework `List<T>` root measures its original native record from one captured span and writes the count and payload into the final byte array. Null lists emit the existing null collection count. Retained output uses the ordinary list formatter.
- **Allocating binary scalar interface writes.** When `IEnumerable<T>`, `ICollection<T>`, `IReadOnlyCollection<T>` or `IReadOnlyList<T>` holds an exact `List<T>` of eligible framework scalars, Next may capture its span once and size and fill the final byte array from that span. The writer uses the original count and raw block format. Other inputs retain the pooled writer and its enumeration rules. Reader state and retained-output operations keep their existing selection.
- **Dense raw binary HashSet writes.** On x64 with SSE, the shared writer may gather four 32-bit values per store in enumeration order when a runtime probe confirms the twelve-byte framework entry stride and the value at offset eight. The complete record is reserved first and each vector load stays within the captured dense entries. Sparse or overlapping storage, unavailable probe data, other widths and platforms use the existing scalar writes. The bounded tail uses the ordinary scalar writer.
- **Checked JSON HashSet traversal.** Next may use live entries of an exact framework `HashSet<T>` after its layout probe succeeds. It checks the enumeration version at each step, including the final step, reads the current entry count, skips vacant entries, and captures each value before its original JSON formatter runs. Derived types and unavailable probes keep framework enumeration.
- **Packed binary priority queues.** On modern 64-bit runtimes, a proven exact framework `PriorityQueue<TElement, TPriority>` with supported integer fields can copy the active heap as one block when actual array addresses prove field order, adjacency and stride match the wire pair. `TryAllocatePriorityQueueRecord` writes the count and packed values into the final array. The retained writer keeps its original room, overlap, header, version and cursor checks. Padded or reordered pairs, unrecognized layouts and unavailable helpers keep the original writer.
- **UTF-16 integer queue writes.** Fixed UTF-16 profiles can use the same two dequeue-order spans as UTF-8. The writer validates each window and checks the queue version before continuing after an output callback.
- **JSON integer linked-list writes.** A verified framework `LinkedList<int>` or `LinkedList<long>` can read its nodes into a temporary span and write a contiguous integer run for a fixed profile. Stage only the elements that fit in the current window at their full scalar widths. A short window writes the current captured item through the ordinary scalar boundary and checks the list version before following its next link.
- **Next immutable linear collections.** An exact framework queue reached through its interface can use the existing two-stack traversal without creating a lazy reversal. JSON queue reads may use a returned element lease and the framework span factory. Stack interfaces can enumerate an exact framework stack directly and build its final nodes from pooled JSON elements or a complete validated raw binary window. Custom interface implementations keep their own enumeration order.
- **Pooled fresh reads.** In ordinary (`Object` mode) binary reads, a reference type with `[LuminPackPoolRent]` rents its instance when the target is null, at the root and as an inline member, and then reads into it like an existing instance. Version-tolerant and reference-tracked modes keep their staged members and late commit.
- **Callbacks** run at their established points and order.
- **JIT tiering hints.** On modern .NET, Core starts its selected collection, string and vector kernels in optimized code. Next preserves its inlining hints and requests first-call optimization for selected element traversal roots outside Unity. Eligible binary write roots over Union elements start optimized where the target supports the hint. Binary string and eligible positional-record loops, including loops over framed nullable and nested collection elements, can tier up and use dynamic PGO. For keyed loops, the other component must be native or eligible for tiering. Native storage, direct pair copies, fixed-object reservations, reads and JSON retain their prior selection. netstandard2.1 omits first-call optimization hints, and Mono, IL2CPP and NativeAOT ignore them.
- **Native nullable collection elements.** Element-wise families may transfer a proven native nullable stride through checked slot or strided reads and writes. This includes `Native` and `Tagged` scalars with one verified native model. Retain family framing, traversal, reuse and enumeration fallbacks. Check the complete addressed range and Boolean storage before the copied elements are published.
- **Binary root entry shapes.** Closed roots can read without renting a context when their analyzed formatter graph needs no operation state. Unknown or custom formatters, schema registration and reference tracking retain the leased state. On modern .NET, an eligible ordinary object span root can outline its checked read when the root or an inlined record contains at least eight modeled members, or the read reaches a collection or Union operation. The wrapper checks the input size before consuming a complete null marker and retains the existing target. Nonnull and empty spans use the outlined checked reader. This split applies to callback-free, nonrecursive, non-versioned ordinary objects without reference tracking, an inherited collection body, bounded-record framing, a rejection, or explicit input limits. Compact roots execute their checked reader directly.
- **Fixed binary root writes.** Eligible native values, marker-prefixed native nullables, fixed sealed objects, versions and raw arrays may fill the final array directly with the existing address-only stores. Arrays of eligible fixed objects may allocate a checked upper bound and trim to the emitted length when a slot is null. An empty retained writer may use the same stores within its existing pinned window and growth threshold, then publish the written length. Append and insufficient-room cases use the established writer. A signed BigInteger uses its checked byte count to reserve the four-byte header and the complete little-endian two's-complement payload in either destination.
- **Native nullable root payloads.** A direct root determines the exact width from presence and reads the present payload through `Nullable.GetValueRefOrDefaultRef`. It stores the payload before the presence marker so that the input may reside in the retained window. An absent value writes only its marker.
- **Bounded retained roots.** Compact portable layouts may write their existing packed standalone fields into a proven retained window. The layout of collection records does not change. An ordinary sealed field-only record with native nullable fields may reserve the maximum encoded length and publish the actual cursor distance. Append and insufficient-room cases use the ordinary writer.
- **Binary root growth and text.** A failed `ReserveRecord` window check calls one non-inlined `GrowRecord` with the writer and cursor by reference. It commits the cursor, rejects negative positions and widths, and checks the absolute end for overflow. Beyond the growth threshold, the owner plans threshold and capacity growth together before changing storage. A failed calculation, rent or pin leaves the previous window at the committed cursor. Successful growth refreshes the window, cursor, record limit and growth threshold. The UTF-16 length short-window helper takes the owner, committed position and window data by value. It tries to encode into the current window before reserving the raw width and checks the threshold at the actual end of a nonnull record. The helper returns the resulting window, cursor and limits, retaining the original window when no growth is needed. If a later step fails after capacity growth succeeds, apply the refreshed window at the committed cursor before rethrowing. For built-in UTF-16 length profiles, a failed string record check with a caller-held cursor calls one non-inlined boundary with the writer and cursor by reference. It commits the cursor and publishes the same short-window result before returning the refreshed cursor. Retained span entries for strings, URI and exact culture records can use the built-in UTF-16 length writer within a proven window. Short Latin-1 stores can inline, while medium and longer records keep their existing outlined encoders. An already initialized framework `Lazy<string>` can use this same empty-window path with its object marker. The ordinary writer invokes an unfinished factory and handles other profiles and append.
- **Closed generic Union dispatch.** A formatter for a closed implicit generic Union compares the exact runtime types of known sealed cases and calls their existing compiled write slots directly. Binary class and interface Union readers switch on the checked name hash. An eligible closed local reader limits the switch to case names reachable for that construction. Unknown cases, registered fallbacks and checked projections keep their existing dispatch rules. Case tags and payloads keep their established representation.
- **Binary compound member boundaries.** Each switch arm keeps the established payload entry or expanded case body. Positional records may call independent non-inlined readers or writers for compound members whose operations exceed the inlining budget. Compact nested records keep their inline path. These boundaries preserve the original profile, state, checks, reuse and publication order.
- **Marker-prefixed nullable writes**. A nullable with a native standalone payload can reserve its marker and value together. A positional record containing only fixed and eligible nullable members can prove room for the complete record once. Short windows reserve the exact width computed from the same captured nullable values. Null markers, storage bytes, 32-bit access and read checks stay in force.
- **Descriptor maps.** A receiving model retains at most eight immutable maps of validated descriptor tables. A cache hit requires exact descriptor bytes, even when a schema identifier matches. Each complete record appends its resolved schema to the operation table. Generated positional and mapped reads share member readers, with a fixed-size presence mask for defaults. A length-prefixed member restores its enclosing read boundary and schema scope on failure.
- **Short Latin-1 string runs**. For binary UTF-16 length records on accelerated 64-bit targets, a contiguous string read may decode a run of short Latin-1 records using one captured readable end. Each record remains bounds-checked and retains its equal existing string, including when other slots change. For a 17–32 character record on AVX2, compare the first 16 characters before loading the trailing block. Reuse requires both comparisons to match.
- **Adjacent binary string fields.** A positional object reader and its inlined ordinary list element reader may group two consecutive wire string fields when both destinations can pass directly by reference and use the same compiled profile. The generator checks the actual Core method signature. Versioned, reference-tracked and Union payload reads keep their own framing, and callback, mirror, volatile, or separately bounded records keep the existing field reads. An accelerated 64-bit UTF-16 length reader checks that a window can hold both four-to-sixteen-byte Latin-1 records before using the short payload kernel. It advances and publishes the first field before it reads the second header. Equal existing values keep their instances, and a later failure retains the first field and its cursor advance. Other strings, profiles and windows read in the original order.
- **Retained writer entry and reset**. An empty retained writer can begin using its current managed window directly. Independent reset clears reference and version state only when that operation populated the corresponding tables. It retains capacity and preserves independent read and write context ownership.
- **Packed priority queue reads**. The checked packed heap reader can validate and copy eight signed 32-bit priorities at a time with AVX2. It resumes four-wide or scalar checking at the first group that needs it. Non-heap input still takes the ordinary enqueue suffix.
- **Medium UTF-16 record writes**. On 64-bit targets with accelerated 256-bit vectors, a contiguous binary UTF-16 length run can use the existing 17-to-32 and 33-to-64 character kernels after proving each full raw bound. Both kernels preserve compact Latin-1 and raw UTF-16 layouts. The run keeps the ordinary short-record stores, the general encoder for larger records and the existing fallback when the bound exceeds the current window.
- **Binary interface collection staging**. Exact framework wrappers can expose validated backing storage to the existing contiguous writers. A framework grouping may lease a temporary array for `ICollection<T>.CopyTo` and write the checked element span in enumeration order. Unknown implementations keep the public enumeration and its publication semantics.
- **Bounded collection staging**. Synchronous collection operations with a known writable prefix can use one exclusive staging slot per closed element type and thread. Rent removes the array from the slot. Return clears all possibly written reference slots and retains at most 4096 elements and 64 KiB; larger requests use the existing shared pool. - **Tiered binary collection reads.** Generated collection read roots that traverse elements or rebuild an interface destination may stay out of their callers to preserve the inline budget inside their loops. The boundary remains tiered. Compact raw-storage readers keep their existing inlining hints.
- **Outlined collection fallbacks.** A collection root may retain its primary element loop and outline a separate traversal or refill fallback. On modern .NET, exact array and list readers can localize reader state for compact positional elements made of fixed scalars and strings that meet the read inlining budget. Shared formatter strategies, callbacks, Union dispatch and compound reads use the original reader. A successful localized read publishes the final reader state. On failure the caller can retain an earlier cursor and see the decoded destination prefix. Writes that can grow use the original writer so its storage follows each relocation. - **Ordinary collection null markers.** A positional collection element can use a single checked marker when its existing fixed payload reader has equivalent storage and validation. Other reused slots keep their early check and reset, including readers that observe the destination in callbacks.
- **Bounded binary text entry loops.** For built-in UTF-16 length profiles, proven dense string-keyed dictionary walks may keep a local cursor and prove the complete key and string or scalar value bound once per pair. Commit the completed prefix before calling the existing writer on the first entry requiring growth. A dense interface write over a verified string-keyed dictionary may call the ordinary value writer through an out-of-line boundary when its callback-free, nonrecursive record has both text and a reservable raw list and fits the direct writer inlining budget.
- **Framed nullable collections.** Zero-based rectangular arrays reserve the existing bounded window for marker-prefixed native payloads and write each record at its actual width. A modern reader can decode framed Int32 values into the matrix or a fresh concurrent queue's staged span using a local cursor within its proven disjoint window. It checks the full input load range and accepts only the existing present and null markers. Short or overlapping windows use checked scalar reads.
- **Nullable collection storage blocks.** On supported modern .NET targets, Next resolves a nullable collection element's layout from its underlying type. - **Nullable binary value storage.** On modern .NET, native reads can fill a nullable's value field after validating the payload, then publish its presence field. ### Options and generation

- Binary string hot paths forward constrained calls on `default(TOptions)` to the selected codec. Inlinable methods must select binary encoding and framing behavior through that codec. Each of the six built-in representations owns its reservation bound, transcoding, checked record skips and cursor publication. Generated batch writes must prove room for the complete record and preserve the published prefix on failure.

- The root JSON profile supplies the document's code unit, grammar and depth check. Fixed and fallback wrappers forward these operations to the same selected profile for the whole document. UTF-8 scalar kernels use a byte code unit and UTF-16 kernels use a char. Name matching, cursor bounds, grammar-state publication and exception offsets retain their original order. The depth check runs after consuming an opening delimiter and incrementing the depth. A nonpositive limit permits unbounded nesting.

- **Compile-time options.** `[LuminPackOption]` scopes (assembly, type, member) and stateless `ILuminPackOptions` profiles are compiled in. There is no runtime options object or mutable global default. JSON encoding, depth and syntax policy apply to a whole document, selected by its root.
- **`UntrustedData`** selects checked binary reads at compile time and is on by default; `UntrustedData = false` generates exactly the trusted code. Untrusted records use the ordinary wire format and writers. Generated reads of objects, version-tolerant records, reference-tracked records and Unions check object markers, Boolean domains, back-reference types, version field widths, compressed counts and declared collection and string limits at the actual read sites, with the root's limits frozen as constants; undeclared limits are unbounded constants. Depth is counted only in recursive types with a declared `MaxDepth`; Reader bounds and stack guards stay on. An explicit hostile-input declaration also selects the strict JSON profile. Input-selected types fail closed. There is no envelope, ambient accounting state or schema prepass.
- **`[LuminPackBounded]`** is a caller guarantee: the bounded record reserves once and drops inner container checks.
- **Automatic generation** discovers declared model graphs and statically required closed operations. Legacy generation-mode settings are ignored. Applications and Unity's predefined assemblies without friend access retain each operation independently for the payloads reached from its bound calls, including their member graphs and Union dependencies. Compiler interception and IL rewriting use the same operation selection. Unresolved serializer expressions, registration and direct generated formatter calls retain all four when the call graph cannot establish a narrower requirement. Libraries retain all four for their discovered payloads because consumer calls are outside the compilation. Registration and wire semantics are independent of this selection. Assembly-level generation options can force retention of an individual operation.
- **Incremental caches** keep exact semantic dependencies, settings, diagnostics and deterministic identities. No `Compilation`, `SemanticModel` or symbol may survive in a cross-compilation cache. Retained-driver output must equal fresh output.

### Optional modules

- Core references neither `LuminPack.Unity` nor `LuminPack.Burst`.
- The `LuminPackBurst` hook table exists only for `netstandard2.1` and follows the [hook ABI](burst-hooks.md). Null slots keep the Core implementation. Burst code is projected from Core sources, never maintained as a second algorithm.

## 3. Safety rules

1. **Reader checks stay on in Release.** The advancing Reader's public `EnsureReadable` and its callers (`Advance`, fixed storage batches, Union framing) are active in every configuration. Do not restore `Conditional("DEBUG")`, wrap checks in `#if DEBUG`, or bypass them for performance.
2. **Check before access.** Generated cursor arithmetic that replaces `Advance` keeps its range check before moving the cursor. Scalar reads and fixed-field fallbacks validate the complete range before any unsafe load or destination write.
3. **Dynamic checks stay.** Collection, string and bulk-payload header and payload validation is mandatory. A count is validated against the remaining input before any allocation sized from it.
4. **Separate unchecked contracts.** Fixed Writer stores into reserved room and address-only raw kernels keep their existing unchecked contracts. This does not permit removing Reader checks or adding blanket Writer checks.
5. **Recursion.** Operations of recursive payloads call `EnsureSufficientStack`, and recursive binary writes check capacity on re-entry.
6. **Signed comparisons.** Range checks against cached ends use signed 64-bit distances so a cursor past the end and negative counts are rejected on every target.
7. **Exceptions** are thrown through `LuminPackExceptionHelper` (runtime) or the generator's own helper. Keep exception types, argument names, cleanup and original stacks.

## 4. SIMD

- Review scalar, 128-bit, 256-bit, 512-bit and ARM64 execution for every SIMD change.
- Guard every ISA-specific operation by its exact required features. Width preference is not hardware support.
- Keep bounded tails, a scalar or portable fallback, zero-length behavior and identical bytes. Never read or write outside a complete validated range.
- A fixed-width algorithm may keep its natural width only with a documented reason.
- Hardware unavailable locally requires CI execution. Compilation or synthetic masks are not hardware validation.

## 5. Performance evidence

- The primary evidence is LuminPack's elapsed time divided by the reference library's, measured on the same machine, fixture, runtime and options, in the same run. Lower is better.
- Report before/after ratios against the same references, repeated samples with dispersion, and allocations. Keep absolute times as supporting evidence.
- Do not infer a win from one nanosecond figure, and do not assume all workloads fluctuate together.
- When machine load makes timing unreliable, compare retained IL and native code instead, and say so.
- Benchmarks of reusable buffers include the reset of each independent record.
