# LuminPack Generator Next: Architecture and Migration Design

Status: working scaffold with the foundation in place. The analysis layer is complete for the current
supported surface, and every payload kind of the current corpus renders inside the Next project:
records, raw and portable structs, collections, dictionaries, circle references and Union roots.
Model equality has reference fast paths, one analysis session is shared per compilation and reused
across nested payloads, referenced-type invalidation is verified, and a same-run benchmark harness
compares the Next and legacy generators. Non-derived class records with auto-properties or included
non-public fields render through the legacy layout mirror, fixed records publish the legacy measurement
entry, version-tolerant class records render their schema prefix and name tables, and class records
with selected constructors, serialization callbacks or a static pool rent render those mechanisms.
The corpus now publishes its IntArray, ListOfInt, String and Int shared formatter owners, so its
generated trees compile without the legacy generator. Other collection, scalar and dictionary owners, the serializer
facade, versioned structs, the remaining constructor/callback/pool shapes, the remaining special
framework types (immutable, concurrent and other original-pipeline families) and analysis diagnostics
remain on the migration plan. CultureInfo is supported end-to-end as the special-type pilot.

## 1. Design philosophy

1. **One analysis boundary.** Roslyn symbols enter `Analysis/TypeModelFactory`; normalized models
   leave it. Nothing below that boundary sees a symbol, a compilation or a legacy analysis object.
2. **The model is the contract.** `Model/` contains immutable, value-equal descriptions of the wire
   facts: identity, members, storage, policies, struct layout, Union cases and reference tracking.
   Renderers never reach back into the compilation.
3. **One renderer per payload kind.** Binary, JSON and Union files have separate entry points.
   A payload kind that is not fully modeled emits nothing rather than partial code.
4. **Explicit incompleteness.** Unsupported shapes return `ModelResult.Incomplete` or
   `ModelResult.Unsupported` with a specific reason. Analysis never crashes generation.
5. **Mechanism preservation.** Local and `As` storage views, virtual Union dispatch and cached
   generic slots, version-tolerant name tables, raw unmanaged paths, `StructLayout`, constructor and
   pool behavior, callbacks, specialized formatters, typed-delegate registration and compiled options
   are retained as the renderers move.
6. **The generated bytes are the product.** Formatting and internal API choices are free only while
   the emitted operations, wire format and public generated surface stay equivalent.

## 2. Architecture

```text
consumer compilation
        |
        v
+----------------------------- Analysis -----------------------------+
| TypeModelFactory                                                  |
|   identity, payload kind, members, storage, WirePolicy,           |
|   struct storage, Union cases, reference tracking                 |
+-----------------------------+-------------------------------------+
                              |
                              v
+------------------------------- Model -------------------------------+
| TypeIdentity / TypeModel / MemberModel / WirePolicy / TypeRef      |
| immutable, value-equal, Roslyn-free                                |
+-----------------------------+-------------------------------------+
                              |
                              v
+---------------------------- Rendering ------------------------------+
| BinaryRenderer / JsonRenderer / UnionRenderer                      |
| RenderModelFactory maps a TypeModel to a PayloadRenderModel        |
| Payload emitters: Binary, JSON, Struct, Union, Circle, Version     |
| CodeWriter -> PublicationLayout -> generated source                |
+--------------------------------------------------------------------+
```

### Incremental granularity

Incrementality belongs to the **generator pipeline**, not to the generated code. The unit is one
attributed payload type: the syntax provider is keyed by the declaration, the transform produces one
`ModeledPayload`, and the output action emits that payload's files. Editing one declaration re-runs
that transform and its outputs; unrelated payloads keep their cached model.

`ModeledPayload` and `ModelResult` implement value equality, and `GeneratorOptions` is cached per
compilation and compared by value. Equality checks compare references before structure, so a cached
model reused inside several parents compares without walking it again. An edit that leaves a payload's
symbol and the project facts unchanged therefore does not re-render its files.

The analysis session is shared by every payload of one compilation. A nested payload is modeled once
per depth and its completed result is reused by every parent that embeds it; a model reached through
a cycle is never published to that cache. Project facts are resolved once per compilation as well.

A referenced type that changes without editing the payload that uses it is observed by the semantic
transform: the model is rebuilt and a changed nested model reaches the parent's output. The probe
verifies both an enum-underlying-type edit (the parent's generated file changes) and a packable child
member edit (the child and its parent report `Modified`, unrelated payloads stay `Unchanged`). What
remains is an optimization, not correctness: every compilation change re-runs the semantic transform
for every attributed declaration, so unchanged models are recomputed and then deduplicated by value
equality. Cross-compilation reuse is tracked in M-14.

Measured with `GeneratorBenchmarks` on a warm process and cold generator state (median of 3 runs;
legacy numbers load the legacy formatter, JSON and facade generators together):

| Corpus | Generator | Full | Comment edit | Member edit | Analysis only |
| --- | --- | ---: | ---: | ---: | ---: |
| 40 records, one type per file | Next | 0.028 s / 18.0 MB | 0.008 s / 0.8 MB | 0.009 s / 1.2 MB | 0.004 s / 0.3 MB |
| 40 records, one type per file | Legacy direct | 0.345 s / 89.5 MB | 0.013 s / 1.9 MB | 0.015 s / 3.2 MB | — |

one-type-per-file corpus shows the per-type granularity. Legacy output includes shared facades and
layout files, so its file count is larger than the payload files the Next run currently covers.

### Layer rules

- `Model/` must not reference `Microsoft.CodeAnalysis`, `LuminDataInfo`, `MetaInfo` or
  `CompiledOptions`.
- `Rendering/` must not reference Roslyn symbols. Project facts arrive through `GeneratorOptions`.
- `Analysis/` is the only place that reads attributes, symbols, layouts and declarations.
- A renderer returns an empty string when it owns nothing for a model. The pipeline adds no source
  file for an empty result.
- Model arrays are copied at construction and treated as immutable. Equality is structural.

## 3. Current coverage

The 220-payload corpus used for verification contains 120 scalar/string records, 40 sequence
records, 10 raw structs, 10 packed structs, 10 Unions with 20 cases and 10 circle-reference nodes.

| Stage | Result |
| --- | --- |
| Analysis | `220 complete, 0 incomplete, 0 unsupported` |
| Payload rendering | all 220 payloads, 440 payload files |
| Shared formatter owners | 4 files: IntArray, ListOfInt, String and Int |
| Compilation of generated output with the Next generator alone | `0` errors |
| Analysis-only cost | 0.041 s median, 2.6 MB on a warm process |
| Current Next generation | 0.140 s median for analysis plus 444 files, 117.8 MB |
| Incremental edit, 40 types | 0.008 s comment edit; 0.009 s member edit |
| Legacy direct pipeline, same 220 payloads | 1.078 s median, 465.7 MB, all three legacy generators |

The legacy direct pipeline still publishes byte-identical files to the legacy original pipeline on this
corpus; that comparison belongs to the legacy tree and is not a Next parity result.

A separate five-type mirror corpus (auto-properties, init-only setters, mixed public fields and
properties, included private and readonly fields) renders 5/5 as ten files with zero compile errors.
Parity against the legacy direct output matched 9/10 files before the record-width fix; the only
mismatch was the missing `MeasureRecord` entry, which the record model now carries. Managed structs of
public fixed scalars, strings and built-in values render as record bodies; derived records, mirrored or
constructed managed structs, callbacks and rent stay unmapped.

A five-record version-tolerant corpus (scalar/string, old name, mirrored, enum and empty) renders 5/5.
Binary output is 5/5 identical to the legacy direct output. JSON initially differed in three files only
because the fresh-result read path was not modeled; records now compute the legacy fresh-result
condition, so the adapter selects the same `var result = reuseExisting ? ...` body. Versioned structs,
versioned callbacks, generic, bounded and non-default profiles stay unmapped.

A seven-record constructor/callback/rent corpus (selected constructors, the four callbacks, a static
pool rent, combinations and mirrored variants) renders 7/7; binary and JSON are 14/14 identical to the
legacy direct output. Ref-returning rent, constructed collection or payload members, trusted
constructed records and derived pooled records stay unmapped.

A one-type CultureInfo corpus renders three files (binary record, JSON record and the shared owner)
with zero compile errors. The binary record, JSON record and CultureInfo owner are identical to the
legacy original-pipeline output after whitespace and assembly-name normalization. The binary member
write keeps the legacy inline block, while reads and JSON use the shared owner. Managed structs and
versioned records containing CultureInfo, dictionaries mixing CultureInfo, and CultureInfo arrays or
keyed collections stay unmapped.

A two-record concurrent/immutable corpus renders seven files (two binary records, two JSON records,
the shared `ConcurrentQueue<int>` and `ImmutableArray<int>` owners, and their `int` element owner)
with zero compile errors. The two binary records, two JSON records and two owners are identical to the
legacy output after whitespace normalization (6/6). The queue writes its counted enumeration in place
and its extension isolates the writer state; the immutable array writes its default marker or storage
span in place.

A second two-record corpus covers `string` elements. It renders seven files with zero compile errors,
and the two binary records, two JSON records and both string owners are identical to the legacy output
after whitespace normalization (6/6). The queue string root is generic over the operation profile, its
counted loop skips the buffer check because the string write performs it, and its read fills pooled
storage through the shared string owner; the immutable string root writes its count and strings through
one profiled call and its read seeds reused elements before the string kernel.

A third corpus covers a packable class element (`Item { int Id; string Name; }`) in both families. It
renders eight files with zero compile errors, and the two binary records, two JSON records and both
payload-element owners are identical to the legacy output after whitespace normalization (6/6). The
owner carries the element's value-equal render model and expands its record body in place: the queue
writes through an isolated operation state and reads without reader isolation, while the immutable
array reserves its header and expands one element per span slot. Elements with nested objects,
collections or no string member stay unmapped, as do the remaining concurrent and immutable families.

The scalar sequence owners are parameterized by element keyword rather than fixed to `int`: a corpus of
`long`, `double` and `Boolean` elements in both families, and a second corpus covering `byte`, `sbyte`,
`short`, `ushort`, `char`, `uint`, `ulong`, `float` and `decimal`, render with zero compile errors and
match the legacy output after whitespace normalization (18/18 and 36/36). Every raw scalar element owns
one `Scalar_<Keyword>` owner file, and the sequence roots read raw storage without the profile; a
Boolean sequence reads through its scalar owner and keeps the profile, as the legacy template does.

The analysis groups every concurrent and immutable collection under one kind, so the render model
checks the declared family before mapping a member. `ImmutableStack<T>` now renders for every raw
scalar element: a thirteen-record corpus renders 52 files with zero compile errors, and its 13 binary
records, 13 JSON records and 13 stack owners are identical to the legacy output after whitespace
normalization (39/39). The stack write reuses the counted enumeration of the queue, while its read
buffers the payload and pushes it back in reverse order; a Boolean element keeps the raw block read,
as the legacy stack emitter does.

`ImmutableList<T>` renders for every raw scalar element too: a thirteen-record corpus renders 52
files with zero compile errors, and its binary records, JSON records, list owners and scalar owners
are identical to the legacy output after whitespace normalization (52/52). The write rents pooled
storage, copies the tree through `CopyTo` and stores the span; the read rebuilds the list from the
pooled span, and the JSON write copies through `LuminTreeStorage` before the element loop.

`ImmutableHashSet<T>` renders for every raw scalar element as well: a thirteen-record corpus renders 53
files (including the shared candidate cache) with zero compile errors, and its binary records, JSON
records, set owners and scalar owners are identical to the legacy output after whitespace
normalization (52/52). The binary write delegates to `LuminTreeStorage.WriteRaw`, the read validates a
weak reuse candidate before creating the set, and the JSON write copies the tree before its element
loop.

`ImmutableQueue<T>`, `ConcurrentStack<T>` and `ConcurrentBag<T>` now have their shared owners and
render paths for every raw scalar element: the queue traverses its two stacks and stages a reversed
backwards stack through a reversal lease with a capacity pre-check, the stack writes one reversed
snapshot and restores order after a JSON read, and the bag tries the validated raw freeze and
otherwise writes one leased snapshot. `Stack<T>` and `SortedSet<T>` are now covered as well: the stack
owner copies the stack once and stores the internal bottom-to-top block, rebuilds it by pushing the
pooled block back, and stages the top-first JSON order for a string element through the shared string
owner; the sorted-set owner stores the ordered tree through `LuminTreeStorage.WriteRaw` and rebuilds
it through `CreateSortedSet` or Clear and Add. These five element shapes were ported in a batch without
a build or parity run, so their verification is still pending. `ImmutableSortedDictionary` and the
dictionary families remain unmapped instead of borrowing the wrong storage protocol, as do packable
stack or bag elements, sorted-set strings and the remaining generic sequence families.

A four-declaration diagnostics corpus (a static class, a ref struct, a class without a public
constructor and a class with 250 serialized members) reports `LuminPack001`, `LuminPack019`,
`LuminPack027` and `LuminPack018` at the declarations, and the 220-payload corpus reports none. An
unexpected rendering failure is reported as `LuminPack099` instead of escaping the pipeline. The
remaining legacy validation (duplicate member names, Union root and case rules, callback, constructor
and rent rules, compiled options and bounded sizes) is not ported yet; unmapped shapes stay silent.

All 220 corpus payloads now render, fixed Union cases publish their own `SerializeUnionAt` cursor
entries, and the collected payload set publishes the corpus's four shared formatter owners. The corpus
therefore compiles with the Next generator alone. Other collection element types, scalar and built-in
owners beyond Int, dictionary families and the serializer facade remain unpublished; shared
publication is tracked in M-01, M-02 and M-09.

## 4. Architecture comparison with Nino

Nino v4 is a source-generated, zero-allocation binary serializer for C#. Its v4 rewrite includes a
truly incremental generator, one file per type, compile-time interceptors, version-tolerant and keyed
formats, reference tracking, pooling, untrusted-input hardening, analyzers, cross-language codegen and
benchmarks against MemoryPack.

| Dimension | LuminPack Next | Nino v4 |
| --- | --- | --- |
| Generator granularity | Per-attributed-type provider; project facts cached per compilation and value-equal; referenced-type dependency tracking still pending | One file per type; only edited types regenerate |
| Intermediate model | Explicit, immutable, value-equal, Roslyn-free model layer | Generator-internal; the emitted formatter is the contract |
| Rendering split | Analysis / model / renderer boundaries, one renderer per payload kind | Formatter generation per type; runtime API in `Nino.Core` |
| Generated size | Large: shared facades, roots, dispatch and per-operation branches | One file per type; oriented toward small output |
| Polymorphism | Virtual Union dispatch, cached generic slots, tags and case slots | Type-id polymorphism without tags |
| Version tolerance | Version-tolerant name tables and schema prefixes | `VersionTolerant` append plus `Keyed` reorder/remove/insert, layout metadata |
| Reference tracking | Circle-reference payloads with slot tables and guards | `trackReferences: true`, cycles and shared references |
| Pooling and reuse | Constructor, pool-rent and reuse paths | `[NinoPooled]`, factories, recyclers, `ref` deserialization |
| Input safety | `EnsureReadable`, checked reads, frozen limits in Release | Untrusted reads with bounded allocation and depth, one exception type |
| Platform matrix | Unity, IL2CPP, 32-bit fixed access, 64-bit raw paths | netstandard2.0 through net10.0, Mono, IL2CPP, trimming, Native AOT, x64/Arm64 |
| Extras | JSON, compiled options as types, registration via typed delegates | ASP.NET Core formatters, TypeScript/Go/Rust codegen, analyzers NINO001-NINO033 |
| Benchmarks | Generation-time and runtime benchmarks exist, but not yet a same-run Nino comparison | Published same-run comparisons against MemoryPack and its own v3 |

### Verdict

**Nino is the more complete product today.** It covers a wider type surface, publishes analyzers and
cross-language codegen, and has a stronger build-time story: one file per type, only edited types
regenerate, and generated output is much smaller.

**LuminPack Next has the cleaner internal architecture.** The explicit analysis/model/render boundary
is easier to test and reason about than emitter-internal state, and the Union dispatch with cached
generic slots is a real mechanism advantage for polymorphic workloads. Compiled options as stateless
types and the Unity/32-bit correctness constraints are also differentiators.

The largest architectural gaps are not in the model: they are incremental granularity and generated
code size. `NextGenerator` combines every symbol with `CompilationProvider`, so a change anywhere
invalidates every model. Nino regenerates only the edited type. Fixing that, and publishing one file
per type instead of shared facades, would close most of the build-time gap.

### Improvement opportunities, in order

1. Finish the renderer migration (collections, portable structs, Unions, circles, versioning).
2. Remove the compilation combine from the per-symbol pipeline; keep project facts in a separate,
   value-equal provider and emit one file per type.
3. Reduce generated source and IL: remove duplicate facade bodies, select operations per call site,
   and share dispatch instead of re-emitting it per payload.
4. Add the analyzer layer (shape diagnostics, invalid options, unsupported layouts).
5. Add keyed version tolerance and publish a stable type-layout metadata contract.
6. Add cross-language codegen and ASP.NET formatters only after the binary surface is stable.
7. Build a same-run benchmark harness against Nino and MemoryPack: payload size, allocations,
   serialization and deserialization throughput, cold and warm generation, per-type cost.

## 6. Decisions and constraints

- `WirePolicy.Default` is **Untrusted**, matching the runtime's documented default and the old
  pipeline. A declaration restores unchecked reads with `UntrustedData = false`.
- The copied renderers keep the legacy `#nullable disable` style; new code in `Analysis/`, `Model/`
  and the renderer entry points is nullable-clean.
- The temporary `Migrated/` snapshot was deleted after the active files moved to
  `Rendering/Emitters/`. The new project carries no `Direct` or `Migrated` names; the old generator
  tree remains only as the migration source for the Union, circle and version emitters.
- The old generator tree currently does not rebuild because of eight pre-existing merge errors. The
  Next copies fix those errors locally; the old tree is not modified.
- `PublicationLayout.Apply` and `LayOutLines` are passthroughs in this milestone. Generated output is
  valid but not byte-identical until M-10 lands.
- `benchmarks/GeneratorBenchmarks` is the same-run harness. It builds the Next generator directly and
  loads the legacy generator DLL reflectively, then reports repeated full, comment-edit, member-edit
  and analysis-only timings with allocations. It measures generator time, not generated size. The
  harness is a separate project excluded from the analyzer compilation.
