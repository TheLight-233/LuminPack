# LuminPack Generator Next: Architecture and Migration Design

Status: working scaffold with the foundation in place. The analysis layer is complete for the current
supported surface, and the payload record, raw-struct, portable-struct, collection, dictionary and
circle-reference renderers run inside the Next project. Model equality has reference fast paths, one
analysis session is shared per compilation and reused across nested payloads, referenced-type
invalidation is verified, and a same-run benchmark harness compares the Next and legacy generators.
Union and version-tolerant rendering remain on the migration plan.

## 1. Design philosophy

1. **One analysis boundary.** Roslyn symbols enter `Analysis/TypeModelFactory`; normalized models
   leave it. Nothing below that boundary sees a symbol, a compilation or a legacy analysis object.
2. **The model is the contract.** `Model/` contains immutable, value-equal descriptions of the wire
   facts: identity, members, storage, policies, struct layout, Union cases and reference tracking.
   Renderers never reach back into the compilation.
3. **One renderer per payload kind.** Binary, JSON and Union files have separate entry points.
   A payload kind that is not fully modeled emits nothing rather than partial code.
4. **Explicit incompleteness.** Unsupported shapes return `ModelResult.Incomplete` or
   `ModelResult.Unsupported` with a specific reason. Analysis never crashes generation.
5. **Mechanism preservation.** Local and `As` storage views, virtual Union dispatch and cached
   generic slots, version-tolerant name tables, raw unmanaged paths, `StructLayout`, constructor and
   pool behavior, callbacks, specialized formatters, typed-delegate registration and compiled options
   are retained as the renderers move.
6. **The generated bytes are the product.** Formatting and internal API choices are free only while
   the emitted operations, wire format and public generated surface stay equivalent.

## 2. Architecture

```text
consumer compilation
        |
        v
+----------------------------- Analysis -----------------------------+
| TypeModelFactory                                                  |
|   identity, payload kind, members, storage, WirePolicy,           |
|   struct storage, Union cases, reference tracking                 |
+-----------------------------+-------------------------------------+
                              |
                              v
+------------------------------- Model -------------------------------+
| TypeIdentity / TypeModel / MemberModel / WirePolicy / TypeRef      |
| immutable, value-equal, Roslyn-free                                |
+-----------------------------+-------------------------------------+
                              |
                              v
+---------------------------- Rendering ------------------------------+
| BinaryRenderer / JsonRenderer / UnionRenderer                      |
| RenderModelFactory maps a TypeModel to a PayloadRenderModel        |
| Payload emitters: Binary, JSON, Struct, Union, Circle, Version     |
| CodeWriter -> PublicationLayout -> generated source                |
+--------------------------------------------------------------------+
```

### Incremental granularity

Incrementality belongs to the **generator pipeline**, not to the generated code. The unit is one
attributed payload type: the syntax provider is keyed by the declaration, the transform produces one
`ModeledPayload`, and the output action emits that payload's files. Editing one declaration re-runs
that transform and its outputs; unrelated payloads keep their cached model.

`ModeledPayload` and `ModelResult` implement value equality, and `GeneratorOptions` is cached per
compilation and compared by value. Equality checks compare references before structure, so a cached
model reused inside several parents compares without walking it again. An edit that leaves a payload's
symbol and the project facts unchanged therefore does not re-render its files.

The analysis session is shared by every payload of one compilation. A nested payload is modeled once
per depth and its completed result is reused by every parent that embeds it; a model reached through
a cycle is never published to that cache. Project facts are resolved once per compilation as well.

A referenced type that changes without editing the payload that uses it is observed by the semantic
transform: the model is rebuilt and a changed nested model reaches the parent's output. The probe
verifies both an enum-underlying-type edit (the parent's generated file changes) and a packable child
member edit (the child and its parent report `Modified`, unrelated payloads stay `Unchanged`). What
remains is an optimization, not correctness: every compilation change re-runs the semantic transform
for every attributed declaration, so unchanged models are recomputed and then deduplicated by value
equality. Cross-compilation reuse is tracked in M-14.

Measured with `GeneratorBenchmarks` on a warm process and cold generator state (median of 3 runs;
legacy numbers load the legacy formatter, JSON and facade generators together):

| Corpus | Generator | Full | Comment edit | Member edit | Analysis only |
| --- | --- | ---: | ---: | ---: | ---: |
| 40 records, one type per file | Next | 0.033 s / 18.0 MB | 0.009 s / 0.7 MB | 0.012 s / 1.1 MB | 0.003 s / 0.3 MB |
| 40 records, one type per file | Legacy direct | 0.368 s / 89.3 MB | 0.019 s / 1.9 MB | 0.018 s / 3.2 MB | — |
| 220 payloads, one file | Next | 0.134 s / 104.7 MB | 0.055 s / 4.4 MB | 0.066 s / 5.1 MB | 0.030 s / 2.1 MB |
| 220 payloads, one file | Legacy direct | 1.050 s / 466.2 MB | 0.087 s / 34.9 MB | 0.078 s / 37.1 MB | — |

The 220-payload corpus is one file, so every edit re-parses and re-runs all 220 transforms; the
one-type-per-file corpus shows the per-type granularity. Legacy output includes shared facades and
layout files, so its file count is larger than the payload files the Next run currently covers.

### Layer rules

- `Model/` must not reference `Microsoft.CodeAnalysis`, `LuminDataInfo`, `MetaInfo` or
  `CompiledOptions`.
- `Rendering/` must not reference Roslyn symbols. Project facts arrive through `GeneratorOptions`.
- `Analysis/` is the only place that reads attributes, symbols, layouts and declarations.
- A renderer returns an empty string when it owns nothing for a model. The pipeline adds no source
  file for an empty result.
- Model arrays are copied at construction and treated as immutable. Equality is structural.

## 3. Current coverage

The 220-payload corpus used for verification contains 120 scalar/string records, 40 sequence
records, 10 raw structs, 10 packed structs, 10 Unions with 20 cases and 10 circle-reference nodes.

| Stage | Result |
| --- | --- |
| Analysis | `220 complete, 0 incomplete, 0 unsupported` |
| Record, collection, portable, raw struct and circle generation | 190 payloads, 380 files |
| Compilation of generated output beside the legacy formatter infrastructure | `0` errors in Next-generated files |
| Compilation of generated output with the Next generator alone | `360` CS0234 errors: the shared collection and string formatter owners are not published yet |
| Analysis-only cost | 0.030 s median, 2.1 MB on a warm process |
| Current Next generation | 0.134 s median for analysis plus 380 payload files, 104.7 MB |
| Incremental edit, 40 types | 0.009 s comment edit; 0.012 s member edit |
| Legacy direct pipeline, same 220 payloads | 1.050 s median, 466.2 MB, all three legacy generators |

The legacy direct pipeline still publishes byte-identical files to the legacy original pipeline on this
corpus; that comparison belongs to the legacy tree and is not a Next parity result.

The 190/220 figure is the honest scope of this milestone. The adapter returns null for payloads whose
supporting renderer or model facts are not ported. Collection members and circle string reads call the
shared `Binary_<assembly>_<type>` formatter owners that the legacy formatter generator publishes; the
Next project does not publish those owners yet, so those payloads compile only beside the legacy
formatter infrastructure. Shared publication is tracked in M-01 and M-09.

## 4. Architecture comparison with Nino

Nino v4 is a source-generated, zero-allocation binary serializer for C#. Its v4 rewrite includes a
truly incremental generator, one file per type, compile-time interceptors, version-tolerant and keyed
formats, reference tracking, pooling, untrusted-input hardening, analyzers, cross-language codegen and
benchmarks against MemoryPack.

| Dimension | LuminPack Next | Nino v4 |
| --- | --- | --- |
| Generator granularity | Per-attributed-type provider; project facts cached per compilation and value-equal; referenced-type dependency tracking still pending | One file per type; only edited types regenerate |
| Intermediate model | Explicit, immutable, value-equal, Roslyn-free model layer | Generator-internal; the emitted formatter is the contract |
| Rendering split | Analysis / model / renderer boundaries, one renderer per payload kind | Formatter generation per type; runtime API in `Nino.Core` |
| Generated size | Large: shared facades, roots, dispatch and per-operation branches | One file per type; oriented toward small output |
| Polymorphism | Virtual Union dispatch, cached generic slots, tags and case slots | Type-id polymorphism without tags |
| Version tolerance | Version-tolerant name tables and schema prefixes | `VersionTolerant` append plus `Keyed` reorder/remove/insert, layout metadata |
| Reference tracking | Circle-reference payloads with slot tables and guards | `trackReferences: true`, cycles and shared references |
| Pooling and reuse | Constructor, pool-rent and reuse paths | `[NinoPooled]`, factories, recyclers, `ref` deserialization |
| Input safety | `EnsureReadable`, checked reads, frozen limits in Release | Untrusted reads with bounded allocation and depth, one exception type |
| Platform matrix | Unity, IL2CPP, 32-bit fixed access, 64-bit raw paths | netstandard2.0 through net10.0, Mono, IL2CPP, trimming, Native AOT, x64/Arm64 |
| Extras | JSON, compiled options as types, registration via typed delegates | ASP.NET Core formatters, TypeScript/Go/Rust codegen, analyzers NINO001-NINO033 |
| Benchmarks | Generation-time and runtime benchmarks exist, but not yet a same-run Nino comparison | Published same-run comparisons against MemoryPack and its own v3 |

### Verdict

**Nino is the more complete product today.** It covers a wider type surface, publishes analyzers and
cross-language codegen, and has a stronger build-time story: one file per type, only edited types
regenerate, and generated output is much smaller.

**LuminPack Next has the cleaner internal architecture.** The explicit analysis/model/render boundary
is easier to test and reason about than emitter-internal state, and the Union dispatch with cached
generic slots is a real mechanism advantage for polymorphic workloads. Compiled options as stateless
types and the Unity/32-bit correctness constraints are also differentiators.

The largest architectural gaps are not in the model: they are incremental granularity and generated
code size. `NextGenerator` combines every symbol with `CompilationProvider`, so a change anywhere
invalidates every model. Nino regenerates only the edited type. Fixing that, and publishing one file
per type instead of shared facades, would close most of the build-time gap.

### Improvement opportunities, in order

1. Finish the renderer migration (collections, portable structs, Unions, circles, versioning).
2. Remove the compilation combine from the per-symbol pipeline; keep project facts in a separate,
   value-equal provider and emit one file per type.
3. Reduce generated source and IL: remove duplicate facade bodies, select operations per call site,
   and share dispatch instead of re-emitting it per payload.
4. Add the analyzer layer (shape diagnostics, invalid options, unsupported layouts).
5. Add keyed version tolerance and publish a stable type-layout metadata contract.
6. Add cross-language codegen and ASP.NET formatters only after the binary surface is stable.
7. Build a same-run benchmark harness against Nino and MemoryPack: payload size, allocations,
   serialization and deserialization throughput, cold and warm generation, per-type cost.

## 6. Decisions and constraints

- `WirePolicy.Default` is **Untrusted**, matching the runtime's documented default and the old
  pipeline. A declaration restores unchecked reads with `UntrustedData = false`.
- The copied renderers keep the legacy `#nullable disable` style; new code in `Analysis/`, `Model/`
  and the renderer entry points is nullable-clean.
- The temporary `Migrated/` snapshot was deleted after the active files moved to
  `Rendering/Emitters/`. The new project carries no `Direct` or `Migrated` names; the old generator
  tree remains only as the migration source for the Union, circle and version emitters.
- The old generator tree currently does not rebuild because of eight pre-existing merge errors. The
  Next copies fix those errors locally; the old tree is not modified.
- `PublicationLayout.Apply` and `LayOutLines` are passthroughs in this milestone. Generated output is
  valid but not byte-identical until M-10 lands.
- `benchmarks/GeneratorBenchmarks` is the same-run harness. It builds the Next generator directly and
  loads the legacy generator DLL reflectively, then reports repeated full, comment-edit, member-edit
  and analysis-only timings with allocations. It measures generator time, not generated size. The
  harness is a separate project excluded from the analyzer compilation.
